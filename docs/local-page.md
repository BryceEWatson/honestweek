# The local page: `honestweek view`

## In plain terms

`honestweek view` opens a page in my browser, served only from my own machine, where I can find the sessions and goals behind a pull request, a commit, a file, a branch or some words, see which sessions worked toward each goal, and replay any session step by step. A Problems page lists 40 known ways AI coding agents go wrong or waste time and tokens, says which showed up in my sessions, links each finding to its step in the replay, and offers fix ideas from published sources for me to adopt myself. Every link, count and step on it says how it's known. It reads my config and a window of my Claude Code and Codex logs, or a made-up demo week, and shows redacted text unless I turn on a switch that shows my private words on my own screen. Nothing is published, nothing leaves the machine, and nothing private is written to disk. This doc says how to run it, what each page does, how it keeps my data private, how it's checked, and what isn't done yet.

## Terms used here

- A **session** is one conversation log from Claude Code or Codex. A **thread** is a group of sessions the logs connect, such as a resumed session and the one it continues.
- The **engine** is honestweek's work-history code. It reads the logs, rebuilds what happened, and tags each step and link with one of four **evidence levels**: **recorded** (a log line or git says so), **derived** (computed from recorded facts), **inferred** (a named rule's best reading, which could be wrong), and **missing** (evidence I'd expect isn't in the logs). An **ambiguous** link is one the records fit more than one way, such as a pull request number two repositories share. [work-history-engine.md](work-history-engine.md) describes the engine.
- **Redaction** replaces private text with markers such as `[redacted:term]`. The **redacted view** is what every page shows unless I turn on the switch below.
- **Show private text** is a switch in every page's header. When it's on, my own screen shows the names, client words and folders that redaction hides. Keys, tokens and passwords stay hidden either way.
- A **display-only** repository is one marked `display` in my config: honestweek never runs git against it. An **outside** session is one whose folder isn't in my config at all. Neither kind ever joins a lookup, a goal or a link between sessions.
- A **goal list** is a JSON file of my goals and the changes made to them, which the engine reads to say which sessions did each goal's work. It's a different file from the goals page's list that `honestweek build` reads.
- The **demo week** is a made-up week of sessions, repositories and goals that honestweek ships, so I can look around before setting anything up.
- The **run key** is a random secret the command makes each time it starts. The page sends it with every data request, and the server refuses any request without it.
- A **one-time code** is what the printed address carries instead of the key. The page trades it for the key once, and then the code stops working.
- The **click-through test** is a test page that drives the real pages in my browser the way a person would, by clicking and typing, and reports each step as pass, fail or skip.
- A **pattern** is one known problem in AI coding agents, such as "says done without checking". The **catalog** is the list of 40 patterns honestweek ships, each with what it looks like, why it matters, how strong the evidence is that it's common, how a log could show it, ways to prevent it, and its published sources.
- A **check** reads the window's history and returns **findings**: one place in one session where a pattern shows, with the step it points at, the rule behind it and its level. A finding is **worth a look** when the check flags it, and a **routine note** when the check records it without flagging it, such as a hedged "should work".
- **Priority** is the tier, High, Medium or Low, a stated rule gives each pattern found in the window. **My priority** is my own tier for a pattern, or "not a problem", which replaces the rule's.
- **Token counts** are what each model call records it read and wrote: input, cache writes, cache reads and output.

## How to run it

```bash
node bin/honestweek.mjs view                  # the last 7 days of my logs
node bin/honestweek.mjs view --days 30        # look further back
node bin/honestweek.mjs view --from 2024-06-10 --to 2024-06-16 --goals goals.json
node bin/honestweek.mjs view --demo           # the made-up week, before setting anything up
node bin/honestweek.mjs view --demo --self-test --no-open
```

- It reads `honestweek.config.json` in the current folder (or `--config <file>`), starts a page on `127.0.0.1`, and opens my browser. `--port <n>` picks the port; otherwise it takes a free one. `--no-open` only prints the address.
- `--days <n>`, or `--from` with `--to`, picks the window: the dates every count and list on the page covers. `--timezone <zone>` reads those dates in another timezone.
- `--goals <file>` names my goal list. I can set `goalsFile` in the config instead. Passing the goals page's list by mistake gets a message that names the difference.
- With no config file in the folder, it opens a Setup page on the same server, with the same key and the same host and site checks, and the terminal says in one line that setup is open in the browser and that `honestweek init` still works for scripts. Setup does what `init` does, with `init`'s own functions: it lists the repositories nearby with each role in plain words, takes one more by its folder path, fills in my email from git and my timezone, asks for the names and client words to keep private in `init`'s words, takes an optional goal list, previews the config, and saves it. Then the same server loads my week and the page goes to Find, with no restart. If loading the week fails (a goal list named with `--goals` that can't be read, say), the config is still saved and the page says to start `view` again. With `--config` naming a missing file, it stops with a message instead. That message, and every command a page names, is written the way I ran honestweek: `honestweek`, `npx` with the package I fetched, or `node` with the script's path. A page names a script or package file by a placeholder (`node <your honestweek folder>/bin/honestweek.mjs`), relative or absolute: a relative path only works from the folder I started in, and a page names steps for another one (set it up in my project folder), and the redacted view never shows a path under my home folder. The command goes through the redactor like every other string, so a private word in a package owner's name stays hidden.
- When my config lists no private words (its `redaction` names, terms and codenames are all empty), it prints a notice that names and client words in my logs show as written, with an example of where to list them, and that `discover` then `harvest` proposes candidates from last week's sessions (both work from a fresh setup; harvest writes them, most frequent first, to the git-ignored `honestweek.harvest.json`). Every page shows the same notice under its header. The demo always has its made-up private word, so it never shows the notice.
- It prints an address with its own one-time code every time it starts, because opening the browser can fail without saying so. Pressing Enter in that terminal prints a fresh one. Ctrl+C stops it.
- `--demo` builds the demo week in a temporary folder, serves only that, and deletes the folder when it stops. It refuses `--config`, `--goals`, `--days`, `--from`, `--to` and `--timezone`, because the demo's data and week are fixed. For that run it treats the made-up project's name as a private word, so the switch has something to show.
- `--self-test` also serves the click-through test and prints its address beside the page's.

## What each page does

**Setup**, only while the folder has no config. Its answers go to the server in a POST body with the run key, never in an address, and nothing typed is stored in the browser. Save writes `honestweek.config.json` and the `.gitignore` lines `init` adds, in the folder `view` started in and nowhere else, and never over a config that's already there, even one that appeared after the page opened: then it changes nothing and says so. An answer that isn't valid JSON, is over 64 KB, has a field Setup doesn't take, or names a folder that isn't there, a repository that isn't a git repository (one marked display only has to exist), a bad email or an unknown timezone is refused with a message, and nothing is written. A repository marked display is only looked at on disk, never passed to git, then or after. Every other page, opened during setup, sends me to it. A config that turns up while Setup is open, from `init` in another terminal say, is loaded on the next request, so the pages reach the week instead of Setup. Setup and Settings refuse a list that names one repository twice by any spelling (a symlink or junction, another case on Windows, a second worktree): one display entry beside a read one is refused with a message, since git would read the display repository through the other; entries that are all display are kept. A network or device path (two slashes at the start, `\\host\share` or `//host/share`) is refused by its shape before any file is looked at, because on Windows even checking it contacts the host. A mapped network drive letter can't be told apart that way, so it isn't caught. It also asks how far back to look, starting on the last week.

**Settings**, linked from every page's header once there's a config. It changes how far back to look, the repositories (add by folder, remove, change a role), the emails, the private words (folded away until I open them) and the goal list. "Review changes" lists what will change in plain words; Save writes it, and the same server reloads the week, so the next page reads the new settings and nothing from the old copy (cached replays, private text) carries over. It keeps the file's own indentation and line endings, and it edits the file as it stands: a field it doesn't show, and one it shows but I didn't change, stays exactly as it was, so a list keeps its order and a repository keeps every field it has. It takes the same key, POST-only routes, host and site checks and size limit as Setup, writes only `honestweek.config.json` in the folder `view` started in (so it's closed for a config named with `--config`, and for the demo), and refuses a save when the file changed on disk after the page opened. Every refusal writes nothing. When I switch a repository to display, the old copy of the week stops before its git step, so git never reads that repository again; the new copy never asks git about it.

**How far back.** `history` in the config: the last n days, from a date, a range of past days (`from` and `to`), or all history. With no `--days`, `--from` or `--to`, `view` reads it; with none saved, it's the last 7 days, as before. A saved choice loads at most the newest 500 MB of log files (`historyLimitMB` raises it, from 50 to 20000), by their last write, sized from file sizes alone before anything is read. On Setup and Settings, one line under the choice says which days it loads, and marks it partial when the limit cuts it short; it comes from `GET /api/window`, whose query holds only the kind, a number, dates and the limit. A line under it says how far back the logs go (the oldest and newest day with a log file, and their total size), and the "?" holds the size of the last week, 30 days, 90 days and year. On Settings, a limit other than the saved one shows its estimated time and memory before saving, and the list of changes repeats it. When that cuts it short, the terminal and a quiet line under every page's header say which days are loaded and how far back the older ones go. The 500 MB comes from a measurement on a synthetic history (the demo week copied 20 times a week, 12 weeks, 444 MB of logs), with the switch off: 37 MB of logs took 19 s and peaked at 154 MB of memory; 148 MB took 70 s and 311 MB; 296 MB took 142 s and 487 MB; 444 MB took 244 s and 685 MB. With Show private text on, 148 MB took 133 s and 411 MB. So, with the switch off, memory grows about 1.3 MB and time about half a second per MB of logs; with it on, about 2 MB and a second. At 500 MB that's about 4 minutes and 760 MB with the switch off, and about 8 minutes and 1.1 GB with it on (estimates from that straight line, not measured at 500 MB, on one machine). The "?" next to How far back shows this machine's own log size and what all of it would load.

Every page's header is one slim line: the name, the four pages (Find, Goals, Replay, and Problems with how many patterns found in the window are High), the window it covers, the Show private text switch, and a "?" button that opens the evidence key: the five words recorded, derived, inferred, missing and ambiguous, each with a one-line meaning. The button is reachable with Tab, and Escape or a click elsewhere closes the key. On the pages, recorded shows as a filled dot, derived as a half-filled one, inferred as a ring and missing as a dashed ring, each a small symbol with its word beside it, or kept for a screen reader where only the symbol shows; ambiguous stays a word. The notice about private words, when my config lists none, is one quiet line under the header, and what the switch promises and that nothing leaves the machine is a quiet line at the foot of every page. A notice I have to act on (no key, a run that stopped, a build that failed) stays prominent under the header. A count is no stronger than the weakest thing it counts: a goal's session count is inferred when a session joins it only by a rule or ambiguously, and a session's prompt count is inferred when the engine only infers who wrote one of them. From the moment it opens, the page says it's connecting; while the data is still being read, it says what it's reading and for how long, counting on between the server's answers, which come slowly while it reads. In demo mode every page carries one quiet line saying the data is made up, and "See your own work" opens the commands to set honestweek up with `init` and run `view` on my own logs, written the way I ran honestweek, and then the Claude Code plugin's install commands, for the weekly summary inside Claude Code.

The pages use the design's colours (a pale ground, white surfaces, one teal accent, and a colour each for High and Medium) and a system font stack in place of the design's IBM Plex Sans and Plex Mono, which are web fonts the page can't load because it makes no network request.

**Find.** The home page is the search box with three "Try" searches, and three cards under it: Worth a look (the top three patterns with a finding worth a look, by priority, linking to the Problems page), Recent sessions (five, with "See the 12 most recent" for the rest, a list the server caps at 12; each says its repo, and says so when it's outside my configured repos), and Your goals (three, with "See all" and a link to the Goals page). One box takes either a reference or words.

- A reference is a pull request (`#12` or its address), a commit id, a file path, or a branch. The page lists the sessions behind it, each with the reasons it's linked and their levels, a link to the record behind each reason, and the goals that session belongs to, with how it joins each one.
- Words list the goals whose titles match, the sessions whose titles match, the branches that contain them, and the prompts that use them. A prompt's text is recorded, because it's in the log; how many of my words it shares is inferred, by a named rule the page shows. "Similar prompts" lists prompts that share a large part of their words with one, also inferred.
- Results open with one summary line for what was found, then a section each (the sessions, then their goals). Each session is one line: its level as a symbol, its title, when it ran, and a short reason that names its level; "More" opens every reason, each with its record, then "Replay from here", "See the record" and its goals. A file or branch lookup also asks the word search, folded as "Also mentioned in words" when the lookup found sessions. The evidence key sits beside the results.
- One short sentence at the foot of the page says what these lookups cover: how many sessions, in my configured repositories, in this window. A closed details line under it says how many display-only and outside sessions they leave out and how a file is found, each count with its level.
- With an empty box, the page shows the three cards, and the "Try" buttons hold the references most sessions in the window point at. Sessions with a prompt come first. A session with no prompt says what opened it instead of "0 prompts", from the record that opened it: a command (with its name when it's a plain slash command), a schedule, or another session or an agent, each recorded; with no such record, that it had no prompt in the window, derived. Its title stays the engine's own, or "Untitled session"; nothing makes one up.

**Search everywhere.** Below the lookups, folded as "Elsewhere on this machine" with its count, the same words search the prompts and titles of every session on the machine in the window, display-only and outside ones included. Each result says which of the three groups it's in, or that its group isn't known when the session isn't in the window's history. It reads each prompt record, and each prompt I typed while the agent was busy, and leaves out what the engine doesn't count as a prompt: the model's summary after a compaction, an interruption marker, and a message another session, an agent or a schedule sent. A busy-time prompt that only the harness's queue record holds isn't searched here yet, though the word lookups above find it in my configured repositories. Each prompt is kept whole, and an excerpt is redacted before it's cut short, so a cut can never show half a private word or half a secret.

**Goals.** Each goal in my goal list shows the sessions working toward it on one timeline I can play, pause, step through and scrub. Each session's place in the goal shows its level, whether it's ambiguous, and whether it's my own assignment (I cited the session in my goal list). Its counts (prompts, tool calls, edits, test runs, pull requests landed) are that session's own, never its whole thread's, because a resumed or forked session in the same thread may belong to another goal. Citations the logs don't back are listed as missing, each with the engine's reason. With no goal list, the page explains what one is and how to give one, and search and replay still work.

**Replay.** Any thread replays to any moment, one lane per agent, with my prompts, the harness and git in their own lanes. Helpers (sub-agents) share one row, folded, until I open it into a lane each; Expand all opens it with every lane. The play, step and prompt buttons, the slider, the time and "step N of M" sit under the timeline; what the marks mean and which kinds of record are shown are each one click away under it. With no thread chosen, it opens the most recent thread in the window, or says there's none and points to search. Opened from a problem finding's "Zoom to these steps", it zooms to that finding's steps and marks only those (see Zoom to these steps below). Each step opens its record in a panel beside the timeline (under it on a phone), above the panel that says what was going on at the playhead, with Previous step and Next step to move through the steps, and:

- what happened, who did it ("You", "a person or a script" for a prompt in a non-interactive run, the main agent, or a named sub-agent), and its level. When the engine only infers that I wrote a prompt, "You" is marked inferred, with the rule.
- its time, and how that time is known, including a line with no time of its own that borrowed one from a neighbouring line, and a sub-agent step the engine moved to just after the call that started it.
- for a command, its output, redacted, then cut short.
- the original log line, re-read from disk only when the panel opens and checked against the fingerprint taken when the history was built, and for a tool call, its recorded result.

Every step on a chart can be reached with the keyboard and opened with Enter, and each chart has a matching list of its steps for a screen reader. Where the page shortens text from the logs, it cuts between words, never inside a hidden part or an id.

**Problems.** The catalog's 40 patterns, checked against the window's sessions in my configured repositories. It opens with "Start with these": the top three High patterns, each with what showed up, one fix idea, "See it happen" (the replay at its first finding worth a look), "Zoom to these steps" for that finding, and Details. Then one table of everything found, High and Medium first, one row per pattern with its priority, its name, what was found and how that count is known; Low is one click away ("Show N low-priority problems"), and so are routine notes, "How priority is set", and the lists of patterns checked and not found, with no check yet, or that a log can't show, none with a priority. The rule gives each found pattern an impact from its catalog group: harm (safety, and correctness and honesty), cost (efficiency and cost) or friction (process and collaboration). Only findings worth a look count, over the whole window, so a longer window can raise a tier. A cost pattern is judged by the tokens its check estimates for its findings worth a look: an estimate worked out from recorded token counts by a named rule (`cost.step`, or the hand-off rule for long sessions), never a measurement, so it carries the inferred level. High is a harm pattern with a finding worth a look worked out from the log's facts, or with 3 or more by a rule's best guess, or a cost pattern whose findings worth a look are estimated at 5% or more of the window's tokens. Medium is a harm pattern with 1 or 2 by a rule's best guess, a cost pattern at 1% to 5%, or a friction pattern with 5 or more. A cost check that counts tokens spent rather than an estimate of waste (small sub-agents) is tiered by its count, like a friction pattern. Low is anything else found, including a pattern whose findings are all routine notes, which a card counts apart as "plus N routine". A share is rounded down where it's shown, so one just under a line never reads as the line itself. Estimates for neighbouring steps overlap, because a later call's context holds an earlier result, so a pattern's estimate can pass the window's total; the page then says so instead of printing a share over 100%. How much one step grew the context is worked out from recorded token counts, but charging that growth to the step's result is the same rule's reading, so those findings are inferred too. Within a tier, patterns sort by the estimated tokens of their findings worth a look, then findings worth a look, then how well established the pattern is. A pattern's count is no stronger than the weakest finding it counts, and a finding that rests on a record the logs don't hold, such as a sub-agent's missing hand-back, is missing rather than derived. Chips filter by catalog group and by status, and each says how many patterns it holds. Each row, opened, shows why it has its priority and "My priority", then:

- what the pattern looks like and why it matters, how strong the evidence is that it's common, and how many sources of each kind back it;
- how it's detected here: the checks that count it, each with its level, and the catalog's signals and known false alarms;
- this window's findings, worth a look first: when, what the log shows in fixed words and numbers, the step's description, the check and rule behind it, its level, and links to the replay at that step, to "Zoom to these steps" with how many steps it marks, to a related step (the failed check, the last edit, my question), and to the goals the session joins;
- fix ideas: the catalog's, and a draft hook, instruction, setting, skill change or workflow to adopt myself. Nothing is applied for me;
- its sources, each with its title, date, kind and what it says. A source's link opens the published page in a new tab when I click it; the page itself fetches nothing.

Nineteen checks cover 18 of the 40 patterns; the page lists each check, how it works, what it read and the rules it names. "My priority" on a found pattern's card moves it to another tier, or to "Not a problem" at the bottom, on this page and on the timelines; choosing the rule's own tier clears it. `problems.html?session=<key>` narrows the page to one session's findings, and `replay.html?session=<key>#<thread>~zoom~<finding key>` is a finding's zoom. The checks, how each works, what it read and what it found, sit below the cards, folded under "How the checks work". With no session in my configured repositories in the window, every check says it had nothing to check, and no pattern reads as checked and not found; the page's first line and the Find card say the same. A token check with no token counts in the window says it didn't run instead of "nothing found", and so does a check that needs text the engine didn't keep, or one that stopped on something in the logs it couldn't read; the other checks still report. A finding at the end of a session's last turn, or on a sub-agent still to hand back, is a routine note marked "may still be running" when the session wrote a record within an hour of when the logs were read. Risky commands count only when git or rm actually runs with the flag, outside quoted text, so a commit message or a search that names `--no-verify` isn't one. A command run through a shell wrapper (`bash -c "..."`, Codex's `bash -lc git push -f`, `eval`) or after `sudo`, `env`, `nohup`, `time`, `exec`, `xargs`, `command` or `builtin` and their options, or a variable assignment, still counts (`command -v` and `sudo -l` only look a command up, so they run nothing); a force-push with lease is a routine note.

**Zoom to these steps.** Every finding, on the "Start with these" cards, in a pattern's opened row, and in the finding box of the replay's record panel (and the strip's card), offers "Zoom to these steps". It opens the replay zoomed from the finding's first step to its last, with a small margin, rings exactly the steps the finding includes and fades every other mark, so they stand out from the rest of the lanes. A one-line bar above the lanes names the pattern, says how many steps are marked, shows the finding's level as its usual symbol and word, and has ◀ and ▶ to step through them in order, each opening its record, with "N of M" and a line for a screen reader. Its "?" opens how the steps are known and anything missing. Leaving the zoom (the fit control, the bar's "Leave", Esc, a double-click, or choosing the whole session) clears the marks and the bar.

The steps are only the ones the finding's check matched and recorded, never a guess at what's between them. Behind the "?", the bar says how that set is known, at the finding's own level (recorded, derived, inferred or missing), and says plainly when the check recorded less than it matched (the line itself reads "21 of 35 steps"): a check that matched 35 steps but keeps the ids of 21 marks those 21 and says so, a check that matches one step marks that one, and the long-session check, which measures model calls rather than steps, marks only the step nearest where its finding starts and says nothing after it is guessed. When the steps sit in more than one agent's lane, or in more than one thread, the line says "2 agents" or "2 threads" and the "?" lists each lane's steps; steps in another thread get a link that opens that thread zoomed the same way. The address carries the finding as `#<thread>~zoom~<finding key>` (and `~<step>` with a record open), so the zoom can be bookmarked, and the browser's Back button returns to the Problems page with the pattern open and the page scrolled where I left it. Stepping through the finding's own steps doesn't add history entries, so one Back is enough.

**Worth a look.** The replay and goal pages show the problem findings for the sessions on screen in a thin strip above the lanes. A badge in the page head always counts them ("2 high, 1 medium worth a look"); the strip itself is off until I turn it on with its switch. Each finding is a dot at its moment, coloured by its pattern's priority, filled when it's worked out from the log's facts and hollow when a rule decided it or a record it expected is missing; a finding that covers a stretch is a faint band, and one pattern's overlapping stretches in a session merge into one. Dots too close to tell apart merge into a count, which zooms in when pressed, or lists its findings when they share a moment or the view can't zoom further. Low-priority findings show when I tick "Show low", and the strip says how many more the Problems page lists for each session. Every mark is a button I can reach with Tab, named for a screen reader; Enter opens a card with the pattern, what the log shows, how it's known, one fix idea, Jump to step and a link to the pattern's card. Escape closes it and puts focus back. While the strip is on, a step's record panel shows the same box for each pattern with a finding worth a look at that step, and a step a finding points at gets a line saying so in the chart's list for a screen reader.

## How it keeps my data private

- **Only my own page can ask.** The server listens on `127.0.0.1` only. It refuses a request whose Host header isn't `127.0.0.1:<port>` or `localhost:<port>`, so a website can't point its own name at the server and read it, and it refuses a data request the browser marks as coming from another site.
- **A key on every data request.** Every data route but the one that trades a code for the key needs the run key, compared in constant time. The key never goes in an address or a process argument: other accounts on some systems can see a process's arguments. The address the command prints or opens carries a one-time code in its fragment (the part after `#`, which the browser never sends to a server), and the page trades it once for the key. To open the browser, the command writes a small redirect file and opens that file, so the code isn't in the opener's arguments either. On Linux and macOS only my account can read the file; on Windows it takes the access list of my temporary folder, which is normally mine alone but which the command doesn't set. Either way, the file is deleted once its code is used, after two minutes if it isn't (its code stops working then too), or when the command stops, whichever comes first.
- **Other tabs.** A new tab opened from a page of this run, such as a replay opened in a new tab, gets the key from this run's other open tabs, in memory. A tab with no way to get the key, such as one left open from an earlier run, shows a notice to open the address the command printed and asks for no data. If the command has stopped, the page says so and stops asking.
- **Data, not scripts.** Answers are JSON, fetched by the page, never served as a script. Every response carries a strict content policy, so a page loads its scripts, styles and data only from this server, plus headers that stop content sniffing, referrers and caching. The pages hold no inline scripts, styles or event handlers. Only reads are allowed, except one route the self-test uses to count leaks.
- **Redacted unless asked.** The server answers with the redacted version unless a request asks for private text, which the page does only while the switch is on. The private version is built in memory the first time it's asked for and is never written to disk. If it fails to build, the page keeps the redacted version and says so. The switch changes only text, never which sessions link to which or which goals they join. The switch starts off every run: it's saved together with the run key, so a setting from an earlier run reads as off.
- **Display-only and outside sessions.** With the switch off, their replays show their text with private words hidden; with it on, in full. Either way they stay out of every lookup, goal and link, and git is never run against a display-only repository.
- **What the browser keeps.** Browsers write addresses into their history and a tab's session storage to disk, so neither holds what I typed or clicked. Addresses carry only made-up ids, plus the commit id or pull request number inside a git step's id, which redaction keeps everywhere. A search gets an id too: the command keeps the typed words in its own memory for this run, and the address carries only the id, so Back, a reload, or turning the switch on brings the search back. Words typed only while the switch was on never come back with it off: their id then brings back an empty box and a note to type them again. Session storage holds only the run key and the switch. Local storage holds one key, `hw.prefs`, and in it only "My priority" for a catalog pattern (the pattern's id, which the catalog ships and is the same on every machine, and one of four tier words) and the strip's two switches. That's a preference about the catalog, not about my logs, so it lasts from one run to the next; nothing typed, no session, step or goal id, and nothing from a log goes in it. The one script that touches it drops anything else on every read and write, including an id the server's catalog doesn't list.
- **Problems.** The checks run once, on the redacted build, over sessions in my configured repositories; display-only and outside sessions aren't checked, as they're left out of lookups and goals. So turning the switch on changes the words a finding shows (its step's description and its session's title come from the build that answers), never which findings there are. To classify a message or compare two calls, the checks read the raw text the engine keeps for them in this program's memory only (its `keepRaw` option), and keep fixed words, counts and one-way fingerprints: a finding's note is built from fixed words and numbers, with token counts written short (340k) so no long run of digits reads as an account number. Every string the problems route sends passes the same redactor as every other answer, the catalog's text included, except a source's title and address: they're the catalog's own published text, the same on every machine and never read from a log, so they show whole and the link works (the redactor used to hide a dollar amount in one title and part of three addresses). So a private word of mine that a source's title happens to contain shows there. Ids, times and dates pass only with an id's, a time's or a date's shape. The rule ids go as a list, since some (`problems.secret-shape`) read as a credential's field name when they're an object's keys.
- **A leak counter.** One function counts leaks in any answer, and both the node tests and the self-test use it. With the switch off, it counts configured terms, names and codenames (inside longer words too), home-folder paths and email addresses. With it on or off, it runs the secrets-only scrubber over every string a second time, on the text as it is and joined onto one line, so a password on the line after its label counts, and each of those both with a JSON escape (`\n`, `\r`, `\t`) read as a break and as written, so a backslash before a word outside JSON text (`C:\token=…`) can't hide it (as written, an escape right before a commit id still reads as a break, since the page shows commit ids on purpose), and it counts a value whose key is sensitive (`"token": "…"`) that the redacted view would hide for its key. The one field it skips is the echo of what I typed into the search box, which comes from my own page, never from a log. With the switch off it also sets aside the Problems catalog's published source titles and addresses, which the page shows whole: in an answer, a source's title and link when the two together are one of the catalog's sources, and on a page, a whole piece of text or address that is exactly a published one. A private word that also appears in a published title isn't a leak there, and it still counts anywhere else. The self-test sends it each piece of a page on its own (each run of text as the page shows it, each address, and each step's description and fields as the page got them), because two pieces joined read as one field: a step ending in `Authorization: [redacted:secret]` followed by a `recorded` chip looks like a header whose value runs on. A step's description is built by the engine from fields it already hid, plus words of its own (` -> ok`), so the server scrubs it once more as a whole. The page's own punctuation next to a hidden value isn't counted either: a description's closing quote glued to a placeholder, when a value was hidden at the very end of a quoted prompt (`DOCS_TOKEN=[redacted:secret]"`), and the `…` that ends a shortened excerpt right after a sensitive key or flag (`--token-file …`), with or without a closing quote glued to it. Each used to read as a value that wasn't hidden. Anything glued on after the quote is still read, a cut mark with more text after it isn't the end of an excerpt and is still read too, and a value shown in either place still counts.

## What's not done yet

- **Speed on real logs.** The page's speed hasn't been measured on a real machine's logs. The targets are the search page ready within 15 seconds, the goal page within 20, about the same again to turn the switch on, and each replay within 5.
- **Loading more history.** A saved choice can start anywhere, up to 500 MB of logs. Loading past that in chunks, following new logs as they're written, and caching each parsed file come next.
- **Problem checks still to come.** 22 of the 40 patterns have no check yet, and say so. Left out on purpose: checks of one person's own written rules (a voice bar, a merge style, no releases), because they're that person's rules rather than a pattern; "edits not committed", because it needs git to say which files are tracked and the checks never run git; and the context-only measures (fix loops, review cost, steps refused), which never make a pattern found. Re-reads count the read tools (Read, NotebookRead, view_image and any read tool given a path), not a shell command that prints a file. The demo week shows only two patterns, both low.
- **Week over week.** A draft fix names nothing yet that a later week could compare to show whether it worked.
- **Not planned here:** saved views at a chosen level of detail for an agent to read, suggesting goals to a first-time user, updating the phone demo page, matching a person's name inside file names, and the prototype's older pages (the three-option chooser, the turn ledger and the week grid).

## Implementation detail

**Files**

- `lib/invocation.mjs`: `commandForm()` works out how honestweek was started (the npm command, `npx` with the spec read from npx's own cache folder, or `node` with the script's path, relative when it's inside the current folder); `bin/honestweek.mjs` records it with `setCommandForm()` and messages read it with `currentCommand()`, which is `honestweek` for code that didn't come through the entry point. `pageCommand()` swaps an absolute path for a placeholder.
- `lib/view/setup.mjs`: `createSetup({ cwd, command, inferEmail, checkGoals, onSaved })` with `info()` (`GET /api/setup`), `preview(body)` and `save(body)` (`POST /api/setup/preview` and `/api/setup/save`, at most `SETUP_MAX_BODY`, 64 KB) and `pending()`. It calls `inferIdentity`, `findRepos`, `displayTest`, `isGitRepo`, `parseWordList`, `buildConfig` and `writeInitFiles(cwd, config, { onlyNew: true })` from `lib/init.mjs`, which writes the config with the `wx` flag and writes nothing else when one exists. `buildConfig` takes `authorEmails` and `goalsFile` for it; `init` passes neither, so its output is unchanged. The server answers the setup routes only when started with `setup`, and swaps in the week's data with `setData` after a save. `lib/view/assets/setup.html` and `setup.js` are the page; `common.js` sends any other page to it while `/api/status` says `setup: true`.
- `lib/view/settings.mjs`: `createSettings({ cwd, editable, checkGoals, history, onSaved })` with `info()` (`GET /api/settings`, including a `version`, a hash of the file), `preview(body)` and `save(body)` (`POST /api/settings/preview` and `/api/settings/save`). It parses the file, replaces only the changed fields (a listed repository is sent as `{ index, role }`), validates with `normalizeConfig`, and writes with `atomicWriteText`. `lib/view/window.mjs`: `planWindow(history, { roots, timezone, now, maxBytes })`, `historyInfo()`, `MAX_LOG_BYTES` and `COST_PER_MB`. `buildWorkHistory` takes a `signal`, checked between files and once before its git step; `createViewData` has `stop()` and a `windowNote`. `lib/view/assets/form.js` holds what Setup and Settings share.
- `lib/view.mjs`: the `view` subcommand. It parses the flags, resolves the window, reads the goal list (`goalsFile` in the config, or `--goals`), builds the demo week with `lib/demo/week.mjs` for `--demo`, starts the server, writes the mode-0600 redirect file in a fresh `mkdtemp` folder with a code that lasts `OPENER_TTL_MS` (two minutes) and removes the file on the same timer, prints the addresses, and prints fresh ones on each line of standard input. It stops on SIGINT, SIGTERM and SIGHUP, and SIGBREAK on Windows. `--port 80` is refused, because a browser leaves that port out of the Host header. `SELF_TEST_PAGE` is `selftest/clickthrough.html`. Exit codes: 0 on Ctrl+C, 1 for a setup error.
- `lib/view/server.mjs`: the loopback server. It reads `lib/view/assets/` once at start (and `lib/view/selftest/` under `/selftest/` with `--self-test`), from a fixed list of names and types. `/api/claim` trades the `X-Honestweek-Code` header for the key; every other `/api/*` route needs `X-Honestweek-Key`. `issueCode(purpose, { ttlMs })` gives a code an optional lifetime; a code past it is used up and refused. GET and HEAD only, plus `POST /api/leak-check` with `--self-test`. The content policy is `CSP` (with `frame-src 'self'` added for the self-test).
- `lib/view/data.mjs`: the data routes and the two builds. It's the only file that turns `private=1` into the engine's `privateText` option. The redacted build passes `hiddenSessions: 'redacted'`. Goals are addressed by `goalKey(rawId)`, a letter hash of the raw goal id, the same in both builds. The replay cache keeps 32 threads per build. A goal member's frames come from `sessionTimeline`, a timeline over that session's own events, sampled with `frameMoments`. `memberCount` gives a goal's session count the weakest level among its members, with the split the home page's goal card shows. Each stored query keeps `typedOff`, whether it was ever typed with the switch off; an `id=` request with the switch off gets `query: null` for one that wasn't. `joinLinesWhereNeeded` also reads a list's text items joined, so a password whose label ends one content block and whose value starts the next is hidden.
- `lib/view/replay-export.mjs`: one thread shaped for the replay page (`REPLAY_EVENT_FIELDS`), frames from the engine's timeline, and the "who" and "how the time is known" labels. `eventRow(h, e, agentsByKey, redact)` passes the engine's `describe(e)` through the build's scrubber.
- `lib/view/word-index.mjs`: search everywhere. It reads prompts and titles line by line into memory, whole, with `queued_command` attachments, leaving out what `lib/replay/claude.mjs` doesn't read as a prompt (`isCompactSummary`, interruption markers, relayed bodies, reminder blocks), labels each hit from the build's own sessions, and collapses, redacts and then cuts each excerpt.
- `lib/view/leaks.mjs`: `createLeakCounter(config)` with `redacted(value)` and `secrets(value)`, and `keyedSecrets(value)` for values under a sensitive key (the full redactor's `deepRedact` rule); `EXEMPT_FIELDS` is `['query']`, and `publishedSources()` is the catalog's source titles and addresses that `redacted(value)` sets aside.
- `lib/view/assets/`: `search` (Find), `goal` and `replay` pages, `common.js` (the page shell, the header's "?" key and Problems count from `/api/problems?summary=1`, the record panel, docked in a page's `#side` column with `setDrawerNav()` for Previous and Next step, and the chart pieces; `clip()` cuts text the server sent only outside a placeholder and between runs of token characters, and the step list, the screen-reader announcements and chart labels keep each piece from the logs in an element of its own, apart from the page's own words), `key.js` (the run key, the switch, and waiting for the build), `evidence.js` (the five words and their inline SVG symbols: `chip()` for a symbol and its word, `sym()` for the symbol with the word kept for a screen reader), `private-text.js` (the switch's handle) and `common.css`.
- `lib/problems/`: `catalog.json` (the 40 patterns and their sources: title, address, date, kind and the catalog's paraphrase; no authors), `classify.mjs` (the text and command classifiers and the `RULES` they name), `context.mjs` (`createContext(h)`: configured sessions only, turns, steps with their fingerprints, token counts joined to the steps they issued and read, and `THRESHOLDS`), `checks.mjs` (`CHECKS` and `runChecks(c)`), `drafts.mjs` (`DRAFTS`), and `index.mjs` (`runProblems(h, { builtT })`, `PATTERN_CHECKS`, `PRIORITY_RULE` and `priorityOf()`). A check that needs token counts or raw text it doesn't have returns `ran: false` with `notRun`. The catalog was converted once from the research step's catalog; the conversion dropped the publisher field (author names), quotes and one personal-blog source, and reworded two paraphrases and dropped one source whose text carried a word the clean-room fence reserves.
- `lib/view/problems-route.mjs`: `createProblemsRoute()`, `redactAnswer()`, `splitUrl()` and `zoomOf()`, which turns a finding's `event`, `related` and `events` into its zoom (the steps this build holds in time order, `total` from the check's `steps` or null when `stepsNear`, `unread`, and `lanes` by thread and agent). Each finding's `key` is `pf-` and a 12-letter hash of its pattern, check, session, steps and times, made unique within one run. `lib/view/data.mjs` asks the redacted build for `usage: true, keepRaw: true` (see [the engine doc](work-history-engine.md)) and runs the checks on it once, on the first problems request; the answer's catalog side is redacted once per mode and kept. `PROBLEM_EXAMPLES` (25) findings per pattern go on the whole page; one session's view and the strip get all of theirs.
- `lib/view/assets/problems.{html,js}`, `strip.js` (`HWS.mount`, `load`, `render`, `note`, called by `replay.js` and `goal.js` after each draw with the chart's own scale), and `prefs.js` (`HWPrefs.createPrefs()`, `effective()`), whose writes all pass `clean()`.
- `lib/view/selftest/clickthrough.{html,js}`: the click-through test and its `SKIPS` list. Its search words and references come from `/api/selftest`, never from its address.
