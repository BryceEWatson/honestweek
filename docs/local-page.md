# The local page: `honestweek view`

## In plain terms

`honestweek view` opens a page in my browser, served only from my own machine, that starts on where my sessions went wrong: a Problems page that checks them against 42 known ways AI coding agents go wrong or waste time and tokens, puts the claims the agent couldn't back first, shows whether each problem happened less than in the window before, links each finding to its step in the replay, and offers a fix I can copy into my own instructions or hooks. One click away, I can find the sessions and goals behind a pull request, a commit, a file, a branch or some words, see which sessions worked toward each goal, and replay any session step by step. Every link, count and step on it says how it's known. It reads my config and a window of my Claude Code and Codex logs, or a made-up demo week, and shows redacted text unless I turn on a switch that shows my private words on my own screen. Nothing is published, nothing leaves the machine, and nothing private is written to disk. This doc says how to run it, what each page does, how it keeps my data private, how it's checked, and what isn't done yet.

## Terms used here

- A **session** is one conversation log from Claude Code or Codex. A **thread** is a group of sessions the logs connect, such as a resumed session and the one it continues.
- The **engine** is honestweek's work-history code. It reads the logs, rebuilds what happened, and tags each step and link with one of four **evidence levels**: **recorded** (a log line or git says so), **derived** (computed from recorded facts), **inferred** (a named rule's best reading, which could be wrong), and **missing** (evidence I'd expect isn't in the logs). An **ambiguous** link is one the records fit more than one way, such as a pull request number two repositories share. [work-history-engine.md](work-history-engine.md) describes the engine.
- **Redaction** replaces private text with markers such as `[redacted:term]`. The **redacted view** is what every page shows unless I turn on the switch below.
- **Show private text** is a switch in every page's header. When it's on, my own screen shows the names, client words and folders that redaction hides. Keys, tokens and passwords stay hidden either way.
- A **display-only** repository is one marked `display` in my config: honestweek never runs git against it. An **outside** session is one whose folder isn't in my config at all. Neither kind ever joins a lookup, a goal or a link between sessions.
- A **goal list** is a JSON file of my goals and the changes made to them, which the engine reads to say which sessions did each goal's work. It's a different file from the goals page's list that `honestweek build` reads.
- The **demo week** is a made-up week of sessions, repositories and goals that honestweek ships, so I can look around before setting anything up.
- The **run key** is a random secret the command makes each time it starts. The page sends it with every data request, and the server refuses any request without it.
- A **one-time code** is what the printed address carries instead of the key. The page trades it for the key once, and then the code stops working.
- The **click-through test** is a test page that drives the real pages in my browser the way a person would, by clicking and typing, and reports each step as pass, fail or skip.
- A **pattern** is one known problem in AI coding agents, such as "says done without checking". The **catalog** is the list of 42 patterns honestweek ships, each with what it looks like, why it matters, how strong the evidence is that it's common, how a log could show it, ways to prevent it, and its published sources. Every source is listed once, with the problems that cite it, in [sources.md](sources.md), which a tool writes from the catalog.
- A **check** reads the window's history and returns **findings**: one place in one session where a pattern shows, with the step it points at, the rule behind it and its level. A finding is **worth a look** when the check flags it, and a **routine note** when the check records it without flagging it, such as a hedged "should work".
- **Priority** is the tier, High, Medium or Low, a stated rule gives each pattern found in the window. **My priority** is my own tier for a pattern, or "not a problem", which replaces the rule's.
- **Token counts** are what each model call records it read and wrote: input, cache writes, cache reads and output.

## How to run it

```bash
node bin/honestweek.mjs view                  # the last 7 days of my logs
node bin/honestweek.mjs view --days 30        # look further back
node bin/honestweek.mjs view --from 2024-06-10 --to 2024-06-16 --goals goals.json
node bin/honestweek.mjs view --demo           # the made-up week, before setting anything up
node bin/honestweek.mjs view --demo --self-test --no-open
```

- It reads `honestweek.config.json` in the current folder (or `--config <file>`), starts a page on `127.0.0.1`, and opens my browser. `--port <n>` picks the port; otherwise it takes a free one. `--no-open` only prints the address.
- `--days <n>`, or `--from` with `--to`, picks the window: the dates every count and list on the page covers. `--timezone <zone>` reads those dates in another timezone.
- `--goals <file>` names my goal list. I can set `goalsFile` in the config instead. Passing the goals page's list by mistake gets a message that names the difference.
- With no config file in the folder, it opens a Setup page on the same server, with the same key and the same host and site checks, and the terminal says in one line that setup is open in the browser and that `honestweek init` still works for scripts. Setup does what `init` does, with `init`'s own functions: it lists the repositories nearby with each role in plain words, takes one more by its folder path, fills in my email from git and my timezone, asks for the names and client words to keep private in `init`'s words, takes an optional goal list, previews the config, and saves it. Then the same server loads my week and the page goes to Problems, the home page, with no restart. If loading the week fails (a goal list named with `--goals` that can't be read, say), the config is still saved and the page says to start `view` again. With `--config` naming a missing file, it stops with a message instead. That message, and every command a page names, is written the way I ran honestweek: `honestweek`, `npx` with the package I fetched, or `node` with the script's path. A page names a script or package file by a placeholder (`node <your honestweek folder>/bin/honestweek.mjs`), relative or absolute: a relative path only works from the folder I started in, and a page names steps for another one (set it up in my project folder), and the redacted view never shows a path under my home folder. The command goes through the redactor like every other string, so a private word in a package owner's name stays hidden.
- When my config lists no private words (its `redaction` names, terms and codenames are all empty), it prints a notice that names and client words in my logs show as written, with an example of where to list them, and that `discover` then `harvest` proposes candidates from last week's sessions (both work from a fresh setup; harvest writes them, most frequent first, to the git-ignored `honestweek.harvest.json`). Every page shows one short line under its header instead, "No private words set, so names show as written.", with a "Set them" link to Settings' private words and the rest of the notice behind its "?". The demo always has its made-up private word, so it never shows the notice.
- It prints an address with its own one-time code every time it starts, because opening the browser can fail without saying so. Pressing Enter in that terminal prints a fresh one. Ctrl+C stops it.
- `--demo` builds the demo week in a temporary folder, serves only that, and deletes the folder when it stops. It refuses `--config`, `--goals`, `--days`, `--from`, `--to` and `--timezone`, because the demo's data and week are fixed. For that run it treats the made-up project's name as a private word, so the switch has something to show.
- `--self-test` also serves the click-through test and prints its address beside the page's.

## What each page does

**Setup**, only while the folder has no config. Save works from the start; Preview shows the file it will write first, if I want to see it. It lists the repositories it found with the folder it started in first, then the most recent commit on any local branch first, each saying when ("last commit 3 days ago"); a display-only repository is never asked, so it sorts after the dated ones. One line under the heading says what featured, reference and display mean, and Settings shows the same line. Its answers go to the server in a POST body with the run key, never in an address, and nothing typed is stored in the browser. Save writes `honestweek.config.json`, `honestweek.config.example.json` if it's missing, and the `.gitignore` lines `init` adds, in the folder `view` started in and nowhere else, and never over a config that's already there, even one that appeared after the page opened: then it changes nothing and says so. An answer that isn't valid JSON, is over 64 KB, has a field Setup doesn't take, or names a folder that isn't there, a repository that isn't a git repository (one marked display only has to exist), a bad email or an unknown timezone is refused with a message, and nothing is written. A repository marked display is only looked at on disk, never passed to git, then or after. Every other page, opened during setup, sends me to it. A config that turns up while Setup is open, from `init` in another terminal say, is loaded on the next request, so the pages reach the week instead of Setup. Setup and Settings refuse a list that names one repository twice by any spelling (a symlink or junction, another case on Windows, a second worktree): one display entry beside a read one is refused with a message, since git would read the display repository through the other; entries that are all display are kept. A network or device path (two slashes at the start, `\\host\share` or `//host/share`) is refused by its shape before any file is looked at, because on Windows even checking it contacts the host. A mapped network drive letter can't be told apart that way, so it isn't caught. It also asks how far back to look, starting on the last week.

**Settings**, linked from every page's header once there's a config. It changes how far back to look, the repositories (listed newest commit first, each with when; add by folder, or "Find new repositories" to list the git repositories next to this folder that the config doesn't have yet, newest first, each with an Add button; remove; change a role), the emails, the private words (folded away until I open them), the goal list, Include /insights and the long-session limit. The long-session limit is how many tokens of context an agent can carry before Problems flags it for going on; empty, the default, turns that check off, since no vendor recommends a number (the Claude API's own compaction starts at 150,000 unless you change it), and "150k" or "150,000" both work. "Review changes" lists what will change in plain words, if I want a look first; Save works from the start, checks every answer again on the server, and writes it, and the same server reloads the week, so the next page reads the new settings and nothing from the old copy (cached replays, private text) carries over. It keeps the file's own indentation and line endings, and it edits the file as it stands: a field it doesn't show, and one it shows but I didn't change, stays exactly as it was, so a list keeps its order and a repository keeps every field it has. It takes the same key, POST-only routes, host and site checks and size limit as Setup, writes only `honestweek.config.json` in the folder `view` started in, plus a `.gitignore` line for it once it lists private words (so it's closed for a config named with `--config`, and for the demo), and refuses a save when the file changed on disk after the page opened. Every refusal writes nothing. When I switch a repository to display, the old copy of the week stops before its git step, so git never reads that repository again; the new copy never asks git about it.

**How far back.** `history` in the config: the last n days, from a date, a range of past days (`from` and `to`), or all history. With no `--days`, `--from` or `--to`, `view` reads it; with none saved, it's the last 7 days, as before. The last week, or the last n days up to 7, always loads every day, whatever its size. A longer choice (more than 7 days, from a date, between two dates, or all history) loads at most the newest 500 MB of log files (`historyLimitMB` raises it, from 50 to 20000), by their last write, sized from file sizes alone before anything is read. On Setup and Settings, one line under the choice says which days it loads ("newest day first" for a week), and marks it partial when the limit cuts it short; it comes from `GET /api/window`, whose query holds only the kind, a number, dates, the limit and, on Setup, the timezone in its form. The line and the load come from the same function with the same timezone, limit and clock, so the line states the days the server then loads; a test compares the two for every kind of choice. A line under it says how far back the logs go (the oldest and newest day with a log file, and their total size), and the "?" holds the size of the last week, 30 days, 90 days and year. On Settings, a limit other than the saved one shows its estimated time and memory before saving, and the list of changes repeats it. When the limit cuts a choice short, the terminal and a quiet line under every page's header say which days are loaded and how far back the older ones go.

**Newest day first.** Any window of more than one day of my own logs loads its newest day on its own first, and the pages answer from it in seconds; then the whole window loads in one pass behind it, and the pages switch over. Until every day is in, nothing reads as complete: the header's window says "so far", a quiet line says "Only 2026-10-04 so far: every count here covers just that day.", a second line says how far the rest has got ("Loading 2026-09-28 to 2026-10-04: 1200 of 8700 log files read."), each Problems row says "N so far" instead of "N now", every "nothing found" says it covers only the days loaded so far, and the trend waits. When every day is in, the page reloads itself, unless I'm typing in a box, when it offers "Update this page" instead. If the rest can't be loaded, the page keeps the first day, still marked partial, and says why. Before the whole window loads, it checks that it fits in the memory the process has left; if it doesn't, it loads the newest days that fit and says so, with the Node option that gives it more. Show private text's second copy is checked the same way. The demo week is small and loads at once.

**What a week costs.** Measured on 4 October 2026 on one Windows machine (Node 22, a 4.1 GB heap limit), on a synthetic week made by `node tools/synthetic-week.mjs <folder> 290 --to <day>`: the demo week's logs copied 290 times across 7 days, each copy with its own session ids, 1,230 MB of logs and 6,380 sessions, its days uneven (4 MB to 678 MB). Loaded the way `view` does, with the switch off, the newest day was ready in 2.6 s when it was the quiet day and 8.4 s when it was the 678 MB day; the whole week was ready at 30 to 37 s, the trend at 39 to 46 s and search everywhere at 43 to 50 s. Memory peaked at 1,381 MB of process memory (1,103 MB of it the JavaScript heap) with the busy day loaded first. Turning Show private text on after that had private text ready at 67 to 74 s, with memory peaking at about 1.6 GB (1.16 GB heap). One pass over the whole week, with no first day before it, was ready at 27 s and peaked at 1,095 MB (932 MB heap), keeping 693 MB of heap after: loading the busy day first costs about 170 MB more at the peak, and the pass's own peak is about a third above what it keeps, so loading one day at a time and merging would save at most about 240 MB, while a session that crosses midnight, a link between days and a goal's members all need the whole window at once. So the week loads in one pass. With a 1.2 GB week before it too (`--weeks 2`, 2,456 MB of logs in all), the trend's first answer, from the week before's newest day, came at 45 s with the quiet day newest and 62 s with the busy one, and the whole week before was in at 84 and 99 s, with a "before" count for 19 patterns; memory peaked at 1,856 to 1,877 MB of process memory (1,626 to 1,634 MB heap), about 500 MB above the week alone, since the week before's build sits beside the week kept in memory until its counts are taken and it's let go. Before this change the same week took 245 s: git was asked about a commit again each time a log named it, and 217 s of the 245 went to those calls; the engine now asks once per repository and commit in a build. The time estimates on Setup and Settings now come from these runs (0.04 s per MB with the switch off and 0.06 s with it on, the slower run); the memory estimates (1.3 MB per MB, and 2 MB with it on) stay, since both runs used less. They're estimates from one synthetic week on one machine: real logs with more commits, or a slower disk, take longer.

Every page's header is one slim line: the name, the four pages (Find, Goals, Replay, and Problems with how many problems there are to fix in the window, counted by the same rule as the Problems headline, so the two match except on a Problems page narrowed to one session, whose headline counts only that session), the window it covers, the Show private text switch, and a "?" button that opens the evidence key: the five words recorded, derived, inferred, missing and ambiguous, each with a one-line meaning. The button is reachable with Tab, and Escape or a click elsewhere closes the key. On the pages, recorded shows as a filled dot, derived as a half-filled one, inferred as a ring and missing as a dashed ring, each a small symbol with its word beside it, or kept for a screen reader where only the symbol shows; ambiguous stays a word. The notice about private words, when my config lists none, is one quiet line under the header, and what the switch promises and that nothing leaves the machine is a quiet line at the foot of every page. A notice I have to act on (no key, a run that stopped, a build that failed) stays prominent under the header. A count is no stronger than the weakest thing it counts: a goal's session count is inferred when a session joins it only by a rule or ambiguously, and a session's prompt count is inferred when the engine only infers who wrote one of them. From the moment it opens, the page says it's connecting; while the data is still being read, it says what it's reading and for how long, counting on between the server's answers, which come slowly while it reads. In demo mode every page carries one quiet line saying the data is made up, and "See your own work" opens the commands to set honestweek up with `init` and run `view` on my own logs, written the way I ran honestweek, and then the Claude Code plugin's install commands, for the weekly summary inside Claude Code.

The pages use the design's colours (a pale ground, white surfaces, one teal accent, and a colour each for High and Medium) and a system font stack in place of the design's IBM Plex Sans and Plex Mono, which are web fonts the page can't load because it makes no network request.

**Light or dark.** A moon or sun button beside the switch, on every page including Setup and Settings, switches the pages between light and dark. Until I click it they follow my system's setting; after that this browser remembers my choice, and the next page opens in it without a flash of the other.

**Find.** One click from Problems in the header, and still at its old address, so a bookmark to it keeps working. It's the search box with three "Try" searches, and three cards under it: Worth a look (the top three patterns with a finding worth a look, by priority, linking to the Problems page), Recent sessions (five, with "See the 12 most recent" for the rest, a list the server caps at 12; each says its repo, and says so when it's outside my configured repos; "All sessions" opens Replay's list of every session in the window), and Your goals (three, with "See all" and a link to the Goals page). One box takes either a reference or words.

- A reference is a pull request (`#12` or its address), a commit id, a file path, or a branch. The page lists the sessions behind it, each with the reasons it's linked and their levels, a link to the record behind each reason, and the goals that session belongs to, with how it joins each one.
- Words list the goals whose titles match, the sessions whose titles match, the branches that contain them, and the prompts that use them. A prompt's text is recorded, because it's in the log; how many of my words it shares is inferred, by a named rule the page shows. "Similar prompts" lists prompts that share a large part of their words with one, also inferred.
- Results open with one summary line for what was found, then a section each (the sessions, then their goals). Each session is one line: its level as a symbol, its title, when it ran, and a short reason that names its level; "More" opens every reason, each with its record, then "Replay from here", "See the record" and its goals. A file or branch lookup also asks the word search, folded as "Also mentioned in words" when the lookup found sessions. The evidence key sits beside the results.
- One short sentence at the foot of the page says what these lookups cover: how many sessions, in my configured repositories, in this window. A closed details line under it says how many display-only and outside sessions they leave out and how a file is found, each count with its level.
- With an empty box, the page shows the three cards, and the "Try" buttons hold the references most sessions in the window point at. Sessions with a prompt, or a program's or a `codex exec` run's starting instruction, come first. A session with no prompt says what opened it instead of "0 prompts", from the record that opened it: a program, a command (with its name when it's a plain slash command), a schedule, or another session or an agent, each recorded; with no such record, that it had no prompt in the window, derived. A session a program started (its first turn's record says `turnOrigin: "sdk"`: a script, the Agent SDK, a headless `claude -p` run, or another session) reads `started by a program`, with the command's name when it opened with one, such as `started by a program: /review`. None of a program's turns counts as a prompt of mine, in any count, in Replay's lane for me, or in any Problems check. A turn recorded `human` was sent from my own session (typed, pasted, or a task prompt I started, which another session may have written), so it counts as mine, but that isn't proof I typed it. The Problems checks still read a program's run, a slash command included, the way they read a `codex exec` run. Its title stays the engine's own; nothing makes one up. A session with no title gets a label from what its log records instead, on every page that names it: "headless run" when its log says `claude -p` or the Agent SDK started it (its records' `entrypoint` starts with `sdk-`) or it's a `codex exec` run, "untitled" otherwise, then when it started and the first eight words of its first prompt in quotes, redacted like the rest of the answer, such as `headless run, Oct 3, 2:14 PM: “Review the open pull request…”`. A display-only or outside session's label leaves its words out, as its title is left out. A session a program opened with a slash command is labelled by the command and when it started, such as `/review, Oct 3, 2:14 PM`. One a program opened with an instruction is labelled "headless run" when its log says so, else "program run", with the first words of the program's instruction. With no prompt, no headless record and no program's turn, it stays "Untitled session".

**Search everywhere.** Below the lookups, folded as "Elsewhere on this machine" with its count, the same words search the prompts and titles of every session on the machine in the window, display-only and outside ones included. Each result says which of the three groups it's in, or that its group isn't known when the session isn't in the window's history. It reads each prompt record, and each prompt I typed while the agent was busy, and leaves out what the engine doesn't count as a prompt: the model's summary after a compaction, an interruption marker, and a message another session, an agent or a schedule sent. In a Codex session it reads only what I typed: the AGENTS.md text, environment and instruction blocks Codex sends as user messages are left out, and so is a `codex exec` run's starting instruction and everything in a child thread, whose messages are its parent agent's hand-offs. A busy-time prompt that only the harness's queue record holds isn't searched here yet, though the word lookups above find it in my configured repositories. Each prompt is kept whole, and an excerpt is redacted before it's cut short, so a cut can never show half a private word or half a secret.

**Goals.** Each goal in my goal list shows the sessions working toward it on one timeline I can play, pause, step through and scrub. Each session's place in the goal shows its level, whether it's ambiguous, and whether it's my own assignment (I cited the session in my goal list). Its counts (prompts, tool calls, edits, test runs, pull requests landed) are that session's own, never its whole thread's, because a resumed or forked session in the same thread may belong to another goal. Citations the logs don't back are listed as missing, each with the engine's reason. With no goal list, the page explains what one is and how to give one, and search and replay still work. A tag beside the title says "Coming soon: Goal discovery".

**Replay.** Any thread replays step by step, one lane per agent, with my prompts, the harness and git in their own lanes, each with its count (a program's command or instruction sits in the agent's lane, marked "A program", never in mine); a lane opens into one row per tool or record kind, and Expand all and Collapse all open or fold every lane (they start open when the chart stays short). Helpers (sub-agents) share one row until it opens into a lane each. With no thread chosen, it opens on a list of the window's sessions to pick from, by the day each started in my configured timezone (each day names its year when the window's days fall in more than one), newest day first and newest first within a day. Each day shows five, with "Show N more" adding up to 20 at a time, and seven days show at once, with "Show earlier days" for the rest, so a busy week stays short. A row has the session's title (redacted unless Show private text is on, like every title), when it started, how long its records span, Claude Code or Codex, its repository, its prompts (or what started it, when it has none), and for a session in a configured repository a link to its findings worth a look on Problems. Display-only and outside sessions are listed too and say so, as on Find's Recent sessions card, and they never join a lookup, a goal or a problem count. Every replay has "← All sessions" back to the list, in a problem's focus too. An old `replay.html#<thread>` address still opens that thread directly. With no session in the window, the page says so and points to search.

- **Long stretches with no new step are squeezed.** In the whole-session view, any stretch longer than two minutes, or a tenth of the session's span, in which no new step starts becomes a narrow break across every lane, so each busy stretch gets room. The times on the axis stay true on both sides of a break. Each break says what filled it, worked out from recorded times, first match wins: "waiting on node --test, 10 min" when a step's recorded span covers at least half of it (its bar runs on across the break), "helper still open, 5 min" when a helper was open across it (the records show it open, not what it did), "no records, 3 min (not idle, just unrecorded)" inside a turn, and "19 min before your next prompt" between turns. Zoomed to a stretch without one, the axis is plain.
- **Steps the agent waited on** (a recorded span of 30 seconds or more) are bars to scale in a lighter style with a solid start, labelled "node --test · 4 min 12 s" where there's room. A failed test run is a taller tick in the high colour.
- **The Problems row** sits at the top of the chart: one dot per finding worth a look in the sessions on screen, at its step's time, in its tier's colour, with the counts by tier above the chart. The count worth a look carries the mark of the weakest finding it counts and says how many of them are only possible (a rule read the words, or a record the check expected is missing), the way the Problems page keeps those apart. With more than one session on screen, "Open in Problems" links each session to its own findings. Each finding's step is ringed in the same colour on its own lane. Routine notes show as dots only after "Show routine notes"; a pattern marked "Not a problem" shows nowhere. Dots too close to tell apart merge into a count that zooms in; it says "findings" rather than "problems" when routine notes are among them.
- **Labels** sit beside marks where there's room and never over another mark or label: each prompt's opening words, messages, edited files, a helper's instruction and its commands, test results, waits, and the harness's "turn ended" and "interrupted".
- **Selecting a step.** A click on a mark or a dot, Enter on either, the step and prompt buttons, Previous problem and Next problem, the slider, or a row in the story all select one step, and everything follows it: the playhead, a "now" line over the chart (time, lane, what it was, its recorded span, its top finding, and "↓ In the steps"), the story's row (its group opened), and the Selected step panel.
- **Just before it.** The bar above the chart names, on one short line, what led to the selected step, zoomed in or not: the step before it in its own lane ("Before it, 2 min earlier: Ran a command: …"), and for a helper's first record, the call in the parent that started it ("Started by …"), with "· started by" beside a helper's opening instruction too. Each is a button that selects that step; when it sits outside the zoom, the zoom widens just enough to hold it. In a problem's focus, ◀ Step goes on past the problem's first step the same way, and the count reads "Before step 1 of N".
- **The story** under the chart: one card per prompt ("You asked", tagged "you corrected it" with the inferred mark when the `prompt.correction` rule says so), then the steps in order with their time, a short mechanical title, the command or the quoted message, a test's recorded pass and fail counts, "waited 4 min 12 s" for a wait, each finding's tier, pattern and level, and the step's own level. "What matters" folds three or more steps in a row of the same kind by the same agent, with no finding, wait or failed test run among them, into one row ("13 shell commands, 2:20:44 PM to 2:21:22 PM", its first command shown, "Show 13 steps"); "Every step" opens every group. An opened group's rows keep each step's result and level. The selected row has "↑ See it in the timeline".
- **A long story stays short.** A session with 5 prompts or fewer shows every card. A longer one shows the card holding the selected step and one on each side, with "Show earlier prompts" and "Show later prompts" (each adds 3, and says how many are left); selecting a step anywhere else, on the chart, with the step controls or the slider, draws its card. A card with more than 15 rows shows its first 10 and "Show N more rows", and always draws the selected row. Measured on 5 October 2026 on one real session of 72 prompts and 2,699 rows at 1280 by 900 pixels: the page went from about 243,000 pixels (270 screens) to 2,833 (3.1 screens) on opening.
- **The Selected step panel** beside the story: the step's time, lane, level and recorded span, its title, the full command or text, its result, and each finding at the step with its tier, its note, "See the fix" (the pattern on the Problems page) and "Zoom to these steps". "At this moment", a closed fold, holds the last thing I asked, what was in progress and the totals so far. ## How it keeps my data private

- **Only my own page can ask.** The server listens on `127.0.0.1` only. It refuses a request whose Host header isn't `127.0.0.1:<port>` or `localhost:<port>`, so a website can't point its own name at the server and read it, and it refuses a data request the browser marks as coming from another site.
- **A key on every data request.** Every data route but the one that trades a code for the key needs the run key, compared in constant time. The key never goes in an address or a process argument: other accounts on some systems can see a process's arguments. The address the command prints or opens carries a one-time code in its fragment (the part after `#`, which the browser never sends to a server), and the page trades it once for the key. The server gives every code a lifetime, so none works forever: a printed address's code stops working 15 minutes after it's printed, so an old address left in the terminal's scrollback can't open the page later, and pressing Enter in the terminal prints a fresh one at any time. To open the browser, the command writes a small redirect file and opens that file, so the code isn't in the opener's arguments either. On Linux and macOS only my account can read the file; on Windows it takes the access list of my temporary folder, which is normally mine alone but which the command doesn't set. Either way, the file is deleted once its code is used, after two minutes if it isn't (its code stops working then too), or when the command stops, whichever comes first.
- **Other tabs.** A new tab opened from a page of this run, such as a replay opened in a new tab, gets the key from this run's other open tabs, in memory. A tab with no way to get the key, such as one left open from an earlier run, shows a notice to open the address the command printed and asks for no data. If the command has stopped, the page says so and stops asking.
- **Data, not scripts.** Answers are JSON, fetched by the page, never served as a script. Every response carries a strict content policy, so a page loads its scripts, styles and data only from this server, plus headers that stop content sniffing, referrers and caching. The pages hold no inline scripts, styles or event handlers. Data routes only read. The actions are POST requests with the same key and checks: Setup's and Settings' Preview and Save, the Include /insights switch, Run /insights, Run with Codex, and the leak counter the self-test uses.
- **Redacted unless asked.** The server answers with the redacted version unless a request asks for private text, which the page does only while the switch is on. The private version is built in memory the first time it's asked for and is never written to disk. If it fails to build, the page keeps the redacted version and says so. The switch changes only text, never which sessions link to which or which goals they join. The switch starts off every run: it's saved together with the run key, so a setting from an earlier run reads as off.
- **Display-only and outside sessions.** With the switch off, their replays show their text with private words hidden; with it on, in full. Either way they stay out of every lookup, goal and link, and git is never run against a display-only repository.
- **What the browser keeps.** Browsers write addresses into their history and a tab's session storage to disk, so neither holds what I typed or clicked. Addresses carry only made-up ids, plus the commit id or pull request number inside a git step's id, which redaction keeps everywhere. A search gets an id too: the command keeps the typed words in its own memory for this run, and the address carries only the id, so Back, a reload, or turning the switch on brings the search back. Words typed only while the switch was on never come back with it off: their id then brings back an empty box and a note to type them again. Session storage holds only the run key and the switch. Local storage holds one key, `hw.prefs`, and in it only "My priority" for a catalog pattern (the pattern's id, which the catalog ships and is the same on every machine, and one of four tier words) and the strip's two switches, plus `light` or `dark` when I've picked one with the theme button. Those are preferences about the catalog and the page, not about my logs, so they last from one run to the next; nothing typed, no session, step or goal id, and nothing from a log goes in it. The one script that touches it drops anything else on every read and write, including an id the server's catalog doesn't list.
- **Problems.** The checks run once, on the redacted build, over sessions in my configured repositories; display-only and outside sessions aren't checked, as they're left out of lookups and goals. So turning the switch on changes the words a finding shows (its step's description and its session's title come from the build that answers), never which findings there are. To classify a message or compare two calls, the checks read the raw text the engine keeps for them in this program's memory only (its `keepRaw` option), and keep fixed words, counts and one-way fingerprints: a finding's note is built from fixed words and numbers, with token counts written short (340k) so no long run of digits reads as an account number. Every string the problems route sends passes the same redactor as every other answer, the catalog's text included, except a source's title and address: they're the catalog's own published text, the same on every machine and never read from a log, so they show whole and the link works (the redactor used to hide a dollar amount in one title and part of three addresses). So a private word of mine that a source's title happens to contain shows there. A fix's text and a test prompt pass the redactor like any other catalog text; a test checks that none of them reads as a secret, since a fix that came out with a marker in it wouldn't be the fix. The trend reads the window just before this one, once, the first time the page asks, with the same options as the redacted build; the checks run on it in memory, only the counts are kept, and its history is let go at once. No text from it reaches an answer. Ids, times and dates pass only with an id's, a time's or a date's shape. The rule ids go as a list, since some (`problems.secret-shape`) read as a credential's field name when they're an object's keys.

- **/insights.** Every string from `/insights` files (a category, the model's description and summary, the session title) passes the same redactor as log text before it reaches the page, with Show private text off and on, so secrets stay hidden either way. Only the files of this window's configured sessions are opened, by an id that must have a session id's shape, so nothing outside `usage-data/facets/` and `usage-data/session-meta/` is read. The toggle and the Run button are POST requests that need the run key and the same host and site checks as every data route. Run is refused with a 409 (`off`) while the toggle is off, so even a request with the key can't start `claude` when the page wouldn't show the button. `claude` is looked for only in absolute folders on the PATH, so a file called `claude` in the current folder is never run, and it gets two fixed arguments and nothing typed. It also gets only the environment variables it needs to start and sign in: the system's own (its path, its home, config and temporary folders, language and timezone), proxy and certificate settings, `CLAUDE_CONFIG_DIR`, any variable starting with `ANTHROPIC_`, `CLAUDE_CODE_` or `DISABLE_` (so an opt-out such as `DISABLE_TELEMETRY` still holds), `DO_NOT_TRACK`, the `AWS_` and Google Cloud variables Claude uses to sign in through Amazon Bedrock or Google Vertex AI, and the home folders of nvm, Volta and asdf, so a `claude` installed with npm finds its `node`. Everything else, such as GitHub, npm and OpenAI tokens, is left out. I checked that `claude` still signs in this way on Windows with a Claude subscription. A sign-in helper script named in Claude's own settings won't see a variable outside that list.
- **Run with Codex.** The button is a POST with the run's key, refused from other hosts and sites like every action, and runs one at a time. Like Run /insights, it's refused with a 409 (`off`) while Include /insights is off. The whole run stops after 20 minutes and one session after 5, with everything that codex started. It runs only a `codex` found in an absolute folder on the PATH, with fixed arguments: nothing from the request reaches its command line or environment. codex gets only the environment variables it needs to start, sign in and reach its service, not other tools' tokens, and any shell command it runs inherits none. Its read-only sandbox still lets it read files I can read, so a session that talked it into looking could; the prompt tells it not to run anything. What it sends and what it keeps pass the full redactor first. honestweek makes no network call itself; codex does, on my own plan.
- **A leak counter.** One function counts leaks in any answer, and both the node tests and the self-test use it. With the switch off, it counts configured terms, names and codenames (inside longer words too), home-folder paths and email addresses. With it on or off, it runs the secrets-only scrubber over every string a second time, on the text as it is and joined onto one line, so a password on the line after its label counts, and each of those both with a JSON escape (`\n`, `\r`, `\t`) read as a break and as written, so a backslash before a word outside JSON text (`C:\token=…`) can't hide it (as written, an escape right before a commit id still reads as a break, since the page shows commit ids on purpose), and it counts a value whose key is sensitive (`"token": "…"`) that the redacted view would hide for its key. The one field it skips is the echo of what I typed into the search box, which comes from my own page, never from a log. With the switch off it also sets aside the Problems catalog's published source titles and addresses, which the page shows whole: in an answer, a source's title and link when the two together are one of the catalog's sources, and on a page, a whole piece of text or address that is exactly a published one. A private word that also appears in a published title isn't a leak there, and it still counts anywhere else. The self-test sends it each piece of a page on its own (each run of text as the page shows it, each address, and each step's description and fields as the page got them), because two pieces joined read as one field: a step ending in `Authorization: [redacted:secret]` followed by a `recorded` chip looks like a header whose value runs on. A step's description is built by the engine from fields it already hid, plus words of its own (` -> ok`), so the server scrubs it once more as a whole. The page's own punctuation next to a hidden value isn't counted either: a description's closing quote glued to a placeholder, when a value was hidden at the very end of a quoted prompt (`DOCS_TOKEN=[redacted:secret]"`), and the `…` that ends a shortened excerpt right after a sensitive key or flag (`--token-file …`), with or without a closing quote glued to it. Each used to read as a value that wasn't hidden. Anything glued on after the quote is still read, a cut mark with more text after it isn't the end of an excerpt and is still read too, and a value shown in either place still counts.

## What's not done yet

- **Speed on real logs.** The page's speed hasn't been measured on a real machine's logs. The targets are the search page ready within 15 seconds, the goal page within 20, about the same again to turn the switch on, and each replay within 5.
- **Loading more history.** A week always loads whole, newest day first; a longer saved choice can start anywhere, up to 500 MB of logs. Loading past that in chunks, following new logs as they're written, and caching each parsed file come next.
- **Problem checks still to come.** 21 of the 42 patterns have no check yet, and say so. Left out on purpose: checks of one person's own written rules (a voice bar, a merge style, no releases), because they're that person's rules rather than a pattern; "edits not committed", because it needs git to say which files are tracked and the checks never run git; and the context-only measures (fix loops, review cost, steps refused), which never make a pattern found. The demo week finds 17 patterns across the three tiers ([docs/demo-week.md](demo-week.md)).
- **Week over week.** A draft fix names nothing yet that a later week could compare to show whether it worked.
- **Not planned here:** saved views at a chosen level of detail for an agent to read, suggesting goals to a first-time user, updating the phone demo page, matching a person's name inside file names, and the prototype's older pages (the three-option chooser, the turn ledger and the week grid).
