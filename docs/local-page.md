# The local page: `honestweek view`

## In plain terms

`honestweek view` opens a page in my browser, served only from my own machine, where I can find the sessions and goals behind a pull request, a commit, a file, a branch or some words, see which sessions worked toward each goal, and replay any session step by step. Every link, count and step on it says how it's known. It reads my config and a window of my Claude Code and Codex logs, or a made-up demo week, and shows redacted text unless I turn on a switch that shows my private words on my own screen. Nothing is published, nothing leaves the machine, and nothing private is written to disk. This doc says how to run it, what each page does, how it keeps my data private, how it's checked, and what isn't done yet.

## Terms used here

- A **session** is one conversation log from Claude Code or Codex. A **thread** is a group of sessions the logs connect, such as a resumed session and the one it continues.
- The **engine** is honestweek's work-history code. It reads the logs, rebuilds what happened, and tags each step and link with one of four **evidence levels**: **recorded** (a log line or git says so), **derived** (computed from recorded facts), **inferred** (a named rule's best reading, which could be wrong), and **missing** (evidence I'd expect isn't in the logs). An **ambiguous** link is one the records fit more than one way, such as a pull request number two repositories share. [work-history-engine.md](work-history-engine.md) describes the engine.
- **Redaction** replaces private text with markers such as `[redacted:term]`. The **redacted view** is what every page shows unless I turn on the switch below.
- **Show private text** is a switch in every page's header. When it's on, my own screen shows the names, client words and folders that redaction hides. Keys, tokens and passwords stay hidden either way.
- A **display-only** repository is one marked `display` in my config: honestweek never runs git against it. An **outside** session is one whose folder isn't in my config at all. Neither kind ever joins a lookup, a goal or a link between sessions.
- A **goal list** is a JSON file of my goals and the changes made to them, which the engine reads to say which sessions did each goal's work. It's a different file from the goals page's list that `honestweek build` reads.
- The **demo week** is a made-up week of sessions, repositories and goals that honestweek ships, so I can look around before setting anything up.
- The **run key** is a random secret the command makes each time it starts. The page sends it with every data request, and the server refuses any request without it.
- A **one-time code** is what the printed address carries instead of the key. The page trades it for the key once, and then the code stops working.
- The **click-through test** is a test page that drives the real pages in my browser the way a person would, by clicking and typing, and reports each step as pass, fail or skip.

## How to run it

```bash
node bin/honestweek.mjs view                  # the last 7 days of my logs
node bin/honestweek.mjs view --days 30        # look further back
node bin/honestweek.mjs view --from 2024-06-10 --to 2024-06-16 --goals goals.json
node bin/honestweek.mjs view --demo           # the made-up week, before setting anything up
node bin/honestweek.mjs view --demo --self-test --no-open
```

- It reads `honestweek.config.json` in the current folder (or `--config <file>`), starts a page on `127.0.0.1`, and opens my browser. `--port <n>` picks the port; otherwise it takes a free one. `--no-open` only prints the address.
- `--days <n>`, or `--from` with `--to`, picks the window: the dates every count and list on the page covers. `--timezone <zone>` reads those dates in another timezone.
- `--goals <file>` names my goal list. I can set `goalsFile` in the config instead. Passing the goals page's list by mistake gets a message that names the difference.
- With no config file, it stops with a message pointing to `honestweek init` to set one up and to `--demo` to look around first. That message, and every command a page names, is written the way I ran honestweek: `honestweek`, `npx` with the package I fetched, or `node` with the script's path. A page shows a path under my home folder as a placeholder (`node <your honestweek folder>/bin/honestweek.mjs`), because the redacted view never shows one.
- When my config lists no private words (its `redaction` names, terms and codenames are all empty), it prints a one-line notice that names and client words in my logs show as written, and where to add them. Every page shows the same notice under its header. The demo always has its made-up private word, so it never shows the notice.
- It prints an address with its own one-time code every time it starts, because opening the browser can fail without saying so. Pressing Enter in that terminal prints a fresh one. Ctrl+C stops it.
- `--demo` builds the demo week in a temporary folder, serves only that, and deletes the folder when it stops. It refuses `--config`, `--goals`, `--days`, `--from`, `--to` and `--timezone`, because the demo's data and week are fixed. For that run it treats the made-up project's name as a private word, so the switch has something to show.
- `--self-test` also serves the click-through test and prints its address beside the page's.

## What each page does

Every page's header shows the window it covers, the Show private text switch, the notice about private words when my config lists none, and the evidence key: the five words recorded, derived, inferred, missing and ambiguous, each with a one-line meaning. A count is no stronger than the weakest thing it counts: a goal's session count is inferred when a session joins it only by a rule or ambiguously, and a session's prompt count is inferred when the engine only infers who wrote one of them. While the data is still being read, the page says what it's reading and for how long. In demo mode every page carries a notice that the data is made up, with the commands to set honestweek up with `init` and run `view` on my own logs, written the way I ran honestweek, and then the Claude Code plugin's install commands, for the weekly summary inside Claude Code.

**Search.** One box takes either a reference or words.

- A reference is a pull request (`#12` or its address), a commit id, a file path, or a branch. The page lists the sessions behind it, each with the reasons it's linked and their levels, a link to the record behind each reason, and the goals that session belongs to, with how it joins each one.
- Words list the goals whose titles match, the sessions whose titles match, the branches that contain them, and the prompts that use them. A prompt's text is recorded, because it's in the log; how many of my words it shares is inferred, by a named rule the page shows. "Similar prompts" lists prompts that share a large part of their words with one, also inferred.
- A coverage line says what these lookups cover (my configured repositories in this window) and how many display-only and outside sessions they leave out.
- With an empty box, the page lists my goals and the most recent sessions, plus "Try" buttons with the references most sessions in the window point at.

**Search everywhere.** Below the lookups, the same words search the prompts and titles of every session on the machine in the window, display-only and outside ones included. Each result says which of the three groups it's in, or that its group isn't known when the session isn't in the window's history. It reads each prompt record, and each prompt I typed while the agent was busy, and leaves out what the engine doesn't count as a prompt: the model's summary after a compaction, an interruption marker, and a message another session, an agent or a schedule sent. A busy-time prompt that only the harness's queue record holds isn't searched here yet, though the word lookups above find it in my configured repositories. Each prompt is kept whole, and an excerpt is redacted before it's cut short, so a cut can never show half a private word or half a secret.

**Goals.** Each goal in my goal list shows the sessions working toward it on one timeline I can play, pause, step through and scrub. Each session's place in the goal shows its level, whether it's ambiguous, and whether it's my own assignment (I cited the session in my goal list). Its counts (prompts, tool calls, edits, test runs, pull requests landed) are that session's own, never its whole thread's, because a resumed or forked session in the same thread may belong to another goal. Citations the logs don't back are listed as missing, each with the engine's reason. With no goal list, the page explains what one is and how to give one, and search and replay still work.

**Replay.** Any thread replays to any moment, one lane per agent, with my prompts, the harness and git in their own lanes. With no thread chosen, it opens the most recent thread in the window, or says there's none and points to search. Each step opens a side panel with:

- what happened, who did it ("You", "a person or a script" for a prompt in a non-interactive run, the main agent, or a named sub-agent), and its level. When the engine only infers that I wrote a prompt, "You" is marked inferred, with the rule.
- its time, and how that time is known, including a line with no time of its own that borrowed one from a neighbouring line, and a sub-agent step the engine moved to just after the call that started it.
- for a command, its output, redacted, then cut short.
- the original log line, re-read from disk only when the panel opens and checked against the fingerprint taken when the history was built, and for a tool call, its recorded result.

Every step on a chart can be reached with the keyboard and opened with Enter, and each chart has a matching list of its steps for a screen reader. Where the page shortens text from the logs, it cuts between words, never inside a hidden part or an id.

## How it keeps my data private

- **Only my own page can ask.** The server listens on `127.0.0.1` only. It refuses a request whose Host header isn't `127.0.0.1:<port>` or `localhost:<port>`, so a website can't point its own name at the server and read it, and it refuses a data request the browser marks as coming from another site.
- **A key on every data request.** Every data route but the one that trades a code for the key needs the run key, compared in constant time. The key never goes in an address or a process argument: other accounts on some systems can see a process's arguments. The address the command prints or opens carries a one-time code in its fragment (the part after `#`, which the browser never sends to a server), and the page trades it once for the key. To open the browser, the command writes a small redirect file and opens that file, so the code isn't in the opener's arguments either. On Linux and macOS only my account can read the file; on Windows it takes the access list of my temporary folder, which is normally mine alone but which the command doesn't set. Either way, the file is deleted once its code is used, after two minutes if it isn't (its code stops working then too), or when the command stops, whichever comes first.
- **Other tabs.** A new tab opened from a page of this run, such as a replay opened in a new tab, gets the key from this run's other open tabs, in memory. A tab with no way to get the key, such as one left open from an earlier run, shows a notice to open the address the command printed and asks for no data. If the command has stopped, the page says so and stops asking.
- **Data, not scripts.** Answers are JSON, fetched by the page, never served as a script. Every response carries a strict content policy, so a page loads its scripts, styles and data only from this server, plus headers that stop content sniffing, referrers and caching. The pages hold no inline scripts, styles or event handlers. Only reads are allowed, except one route the self-test uses to count leaks.
- **Redacted unless asked.** The server answers with the redacted version unless a request asks for private text, which the page does only while the switch is on. The private version is built in memory the first time it's asked for and is never written to disk. If it fails to build, the page keeps the redacted version and says so. The switch changes only text, never which sessions link to which or which goals they join. The switch starts off every run: it's saved together with the run key, so a setting from an earlier run reads as off.
- **Display-only and outside sessions.** With the switch off, their replays show their text with private words hidden; with it on, in full. Either way they stay out of every lookup, goal and link, and git is never run against a display-only repository.
- **What the browser keeps.** Browsers write addresses into their history and a tab's session storage to disk, so neither holds what I typed or clicked. Addresses carry only made-up ids, plus the commit id or pull request number inside a git step's id, which redaction keeps everywhere. A search gets an id too: the command keeps the typed words in its own memory for this run, and the address carries only the id, so Back, a reload, or turning the switch on brings the search back. Words typed only while the switch was on never come back with it off: their id then brings back an empty box and a note to type them again. Session storage holds only the run key and the switch.
- **A leak counter.** One function counts leaks in any answer, and both the node tests and the self-test use it. With the switch off, it counts configured terms, names and codenames (inside longer words too), home-folder paths and email addresses. With it on or off, it runs the secrets-only scrubber over every string a second time, on the text as it is and joined onto one line, so a password on the line after its label counts, and it counts a value whose key is sensitive (`"token": "…"`) that the redacted view would hide for its key. The one field it skips is the echo of what I typed into the search box, which comes from my own page, never from a log. The self-test sends it each piece of a page on its own (each run of text as the page shows it, each address, and each step's description and fields as the page got them), because two pieces joined read as one field: a step ending in `Authorization: [redacted:secret]` followed by a `recorded` chip looks like a header whose value runs on. A step's description is built by the engine from fields it already hid, plus words of its own (` -> ok`), so the server scrubs it once more as a whole.

## How it's checked

- The node suite (`node --test`) covers the named tests in the plan that don't need a browser: the security refusals, the run key and one-time codes, the switch and the replay cache, a failed private build, the restart case, privacy in every answer, search and goals, the replay fields and the record panel, the demo and no-config cases, and the page files. A contract test pins each field a page reads to the answer that carries it, because the pages and the server were built separately and drifted apart once.
- The click-through test runs in my browser with `--self-test`. It drives search, goals and replay at desktop and phone width, flips the switch, and counts every page error, console error and content-policy violation as a failure. A step may skip only for a reason on its named list, each of which can't apply to some data.
- Its **first run** group checks what a newcomer sees: while the data is still being read, the page says what it's reading and for how long (skipped as `built-before-test` when the data was ready before the test started); the home page says what to type and offers a first search, or says why it has none; with no private words, every page shows the notice (skipped as `private-words-set` otherwise); and with no goal list, the goals page says what one is and the command that gives one (skipped as `goal-list-set` otherwise). `?only=first-run` runs just this group.
- `test/first-run.test.mjs` runs a new user's commands through the real entry point, with no browser and no network: `honestweek` with no arguments, `view` before any setup, `init` with its answers piped in (each question's wording, the repositories with a worktree folded in, the private words, and `view` as the next step), then `view --no-open` until its data is ready, and a stop. It also checks that `npm pack` would ship the entry point and the pages.
- On the demo week, on 3 October 2026, it reported 64 passed, 0 failed and 3 skipped, at 1280 and 375 pixels wide, with the switch off and on, with no page error and no content-policy violation. That run had the engine change that shows display-only and outside sessions as redacted text; without it, the same week reports 62 passed, 0 failed and 5 skipped, the two more being `no-display-session` and `no-outside-session`. The three skips are on the named list and can't apply to the demo week, which has no prompt whose author is only inferred, no prompt from a non-interactive run, and no sub-agent step moved after the call that started it: `no-inferred-author`, `no-script-prompt` and `no-moved-time`.
- On a week of my own logs, on 3 October 2026, it reported 64 passed, 0 failed and the same 3 skipped, in a 1280-pixel-wide browser, with the switch off and on, with no page error. Its first run there failed 5 steps, none of them a leak: a search word that is also the name of the replay address's own parameter, and text the leak counter read joined to its neighbour, where the end of one piece and the start of the next looked like a field and its value.

## What's not done yet

- **Speed on real logs.** The page's speed hasn't been measured on a real machine's logs. The targets are the search page ready within 15 seconds, the goal page within 20, about the same again to turn the switch on, and each replay within 5.
- **Two engine changes it relies on ship separately.** One makes redaction fast on short text. The other hides private words before the engine cuts text short, and adds the option that shows display-only and outside sessions as redacted text. Without that option, those sessions show only the kind and time of each step.
- **Loading more history.** Picking a start point, following new logs as they're written, loading all history in chunks, and caching each parsed file come next. Until then, `--days` or `--from` and `--to` set the window.
- **Not planned here:** saved views at a chosen level of detail for an agent to read, suggesting goals to a first-time user, updating the phone demo page, matching a person's name inside file names, and the prototype's older pages (the three-option chooser, the turn ledger and the week grid).

## Implementation detail

**Files**

- `lib/invocation.mjs`: `commandForm()` works out how honestweek was started (the npm command, `npx` with the spec read from npx's own cache folder, or `node` with the script's path, relative when it's inside the current folder); `bin/honestweek.mjs` records it with `setCommandForm()` and messages read it with `currentCommand()`, which is `honestweek` for code that didn't come through the entry point. `pageCommand()` swaps an absolute path for a placeholder.
- `lib/view.mjs`: the `view` subcommand. It parses the flags, resolves the window, reads the goal list (`goalsFile` in the config, or `--goals`), builds the demo week with `lib/demo/week.mjs` for `--demo`, starts the server, writes the mode-0600 redirect file in a fresh `mkdtemp` folder with a code that lasts `OPENER_TTL_MS` (two minutes) and removes the file on the same timer, prints the addresses, and prints fresh ones on each line of standard input. It stops on SIGINT, SIGTERM and SIGHUP, and SIGBREAK on Windows. `--port 80` is refused, because a browser leaves that port out of the Host header. `SELF_TEST_PAGE` is `selftest/clickthrough.html`. Exit codes: 0 on Ctrl+C, 1 for a setup error.
- `lib/view/server.mjs`: the loopback server. It reads `lib/view/assets/` once at start (and `lib/view/selftest/` under `/selftest/` with `--self-test`), from a fixed list of names and types. `/api/claim` trades the `X-Honestweek-Code` header for the key; every other `/api/*` route needs `X-Honestweek-Key`. `issueCode(purpose, { ttlMs })` gives a code an optional lifetime; a code past it is used up and refused. GET and HEAD only, plus `POST /api/leak-check` with `--self-test`. The content policy is `CSP` (with `frame-src 'self'` added for the self-test).
- `lib/view/data.mjs`: the data routes and the two builds. It's the only file that turns `private=1` into the engine's `privateText` option. The redacted build passes `hiddenSessions: 'redacted'`. Goals are addressed by `goalKey(rawId)`, a letter hash of the raw goal id, the same in both builds. The replay cache keeps 32 threads per build. A goal member's frames come from `sessionTimeline`, a timeline over that session's own events, sampled with `frameMoments`. `memberCount` gives a goal's session count the weakest level among its members, with the split the home page's goal card shows. Each stored query keeps `typedOff`, whether it was ever typed with the switch off; an `id=` request with the switch off gets `query: null` for one that wasn't. `joinLinesWhereNeeded` also reads a list's text items joined, so a password whose label ends one content block and whose value starts the next is hidden.
- `lib/view/replay-export.mjs`: one thread shaped for the replay page (`REPLAY_EVENT_FIELDS`), frames from the engine's timeline, and the "who" and "how the time is known" labels. `eventRow(h, e, agentsByKey, redact)` passes the engine's `describe(e)` through the build's scrubber.
- `lib/view/word-index.mjs`: search everywhere. It reads prompts and titles line by line into memory, whole, with `queued_command` attachments, leaving out what `lib/replay/claude.mjs` doesn't read as a prompt (`isCompactSummary`, interruption markers, relayed bodies, reminder blocks), labels each hit from the build's own sessions, and collapses, redacts and then cuts each excerpt.
- `lib/view/leaks.mjs`: `createLeakCounter(config)` with `redacted(value)` and `secrets(value)`, and `keyedSecrets(value)` for values under a sensitive key (the full redactor's `deepRedact` rule); `EXEMPT_FIELDS` is `['query']`.
- `lib/view/assets/`: `search`, `goal` and `replay` pages, `common.js` (the page shell, the record panel and the chart pieces; `clip()` cuts text the server sent only outside a placeholder and between runs of token characters, and the step list, the screen-reader announcements and chart labels keep each piece from the logs in an element of its own, apart from the page's own words), `key.js` (the run key, the switch, and waiting for the build), `evidence.js` (the five words), `private-text.js` (the switch's handle) and `common.css`.
- `lib/view/selftest/clickthrough.{html,js}`: the click-through test and its `SKIPS` list. Its search words and references come from `/api/selftest`, never from its address.

**Routes and the fields the pages read**

Every data answer carries `view: { asked, shown, note, privateState, window, demo }`. `asked` and `shown` are `redacted` or `private`; `note` says why the private version wasn't served; `demo` is the demo notice (`{ notice, commands: [{ step, command }] }`) or null.

| Route | Answer |
| --- | --- |
| `/api/status` | `state`, `elapsedMs`, `reading`, `failed`, `window`, `builds: { redacted, private }` (each `{ state, ms, elapsedMs, failed }`, the redacted one with `reading`), `search`, `goalList`, `demo`, `command` (how I run honestweek, for the commands a page names), `privateWords: { count, note }` (`note` is the notice, or null), `selfTest`, `evidenceKey`. Asked with `private=1`, it starts the private build. It never holds the key. |
| `/api/home` | `coverage` (`sessionsRead`, `configured`, `display`, `outside`, `excludedFromLookups`, `filesUnnamed`, each `{ value, evidence }`), `goals` (`key`, `title`, `state`, `members`, `unmatched`), `goalList: { given, note }`, `recent` (session rows with `session`, `thread`, `title`, `goals`, `prompts`), `try` (`{ kind, text }`). |
| `/api/lookup?q=` or `?id=` | the engine's lookup with its reading of the reference in `parsed`, `kind`, `notes`, session rows with their `goals`, `repositories` for a file, and `goals` (each with the `sessions` the lookup found: `session`, `evidence`, `ambiguous`, `assigned`). An answer to `q=` carries `queryId`; an answer to `id=` echoes the typed text in `query`. |
| `/api/words?q=`, `?id=` or `?similar=` | `goals` (with `matchedIn`), `sessions`, `branches`, `prompts` (each recorded, with `score: { value, of, evidence: 'inferred', rule: 'view.shared-words' }`); with `similar=`, the list is in `similar`. |
| `/api/search?q=` or `?id=` | `ready: false` with `state` and `note` while the index is read; then `ready: true`, `indexed`, `sessions`, `total`, and `results` (`session`, `thread`, `group`, `inWindow`, `name`, `snippets`). |
| `/api/goal?key=` | `members` (with `evidence`, `ambiguous`, `assigned`, `joins`), `unmatched` (as missing), `sessions`, `agents`, `events`, and `frames` keyed by session. No log lines. |
| `/api/replay?thread=` or `?session=` | `thread`, `session` (with `turns`), `sessions`, `agents`, `events`, `frames`, `rules`, `coverage`. With neither, the most recent thread. An id the window doesn't hold, or a window with no thread, gives `thread: null` with an `empty` line naming the window. No log lines. |
| `/api/record?event=` | `event`, `who`, `timeNote`, `records` (each with `part`: `step`, `result` or `copy`, plus `line`, `verified`, `note`, `record`), `output: { text, cut }` for a command, `tests`. |
| `/api/selftest` | With `--self-test` only: `words`, `examples` (a squash-merged commit and a file a prompt names, each checked by its lookup), `goal`, and a session of each group. |
| `POST /api/leak-check` | With `--self-test` only: the leak counter's counts for the posted text, never the text. With `parts=1` the text is a JSON list, each item checked on its own; anything else gets 400. |

A frame's counts carry their levels under the frame's own names (`testsPassed`, `testsFailed`, `commits`), which `common.js` reads beside the engine's timeline names.

**Tests**

- The data tests run on `test/fixtures/view/week.mjs`, the demo week seeded with made-up private terms, a name, secrets (including a password on the line after its label) and the ids the switch is meant to show.
- `test/private-text.test.mjs` allows only `lib/view/data.mjs`, `lib/view/word-index.mjs` and `lib/view/leaks.mjs`, beside the engine and the redactor, to name the private-text option. `test/site-cleanroom.test.mjs` fences `lib/view/`, its tests and this doc.
