# The work-history engine

## In plain terms

The work-history engine reads my local AI coding session logs and rebuilds what happened as a timeline I can replay to any moment and drill into, from a week down to the single log line behind each step. Every step it shows carries a tag saying how it's known: a log line says so, it was computed from log lines, a named rule interpreted it, or the evidence I'd expect is missing. It never invents working time, a count of agents "working", a cause, or a reason. It also works backwards: given a pull request, a commit, a file, or a branch, it finds the sessions behind it, and given my own list of goals, it says which sessions did each goal's work and how each link is known. It doesn't change any report honestweek already makes. Its screen is `honestweek view`, a page on my own machine described in [local-page.md](local-page.md), and a small developer tool also prints each level so the model can be checked from a terminal.

## What it's for

honestweek's reports say what landed. This engine is the layer under `honestweek view`, the page that shows how it got there: the prompts, the sub-agents an agent started, the commands it ran, the tests, the interruptions, and what git says happened to the result. The page is its own design, in [local-page.md](local-page.md); the engine only promises a complete, checkable model to draw from.

A few terms used below:

- The **harness** is the program that runs an AI agent and writes its log: Claude Code or Codex.
- A **session** is one conversation log file. A **sub-agent** is a helper an agent started; Claude Code writes its transcript beside the session, and Codex writes a separate log (a **child thread**) that names its parent.
- A **turn** runs from a prompt (or a notice that wakes the agent) to the next one.
- A **thread** is a group of sessions the records themselves connect: a resumed session that copies an earlier one, or a message one session sent to another.
- A **hook** is a script the harness runs at set points, such as before a command or at the end of a turn. Some hooks refuse a step.
- **Compaction** is the harness shortening the conversation it sends to the model when it grows too long.
- A **reference** points at the exact bytes of one log line and carries a fingerprint (a digest) of them, so drilling down re-reads that line and refuses to show it if it changed.

## The four evidence levels

| Level | Meaning | Example |
| --- | --- | --- |
| recorded | A log line or git says it directly. | A tool call, its result, a git commit's date. |
| derived | Computed from recorded values only. | Time between a call and its result; lines added in a recorded patch; a pass/fail count read from a test runner's printed summary. |
| inferred | A named rule interpreted a record, and could be wrong. | Calling a prompt a correction; calling a command a test run (so the counts of runs that passed or failed are inferred too); treating a session as started from another's task suggestion; reading a commit id from printed output; matching a pull request to the default-branch commit whose subject names it; deciding which file holds the original of a record a resumed session copied. |
| missing | Evidence I'd expect is absent. | A call with no recorded result; a sub-agent whose starting call is in no log. |

Every step stores the four apart, and building a history fails if a step has no reference or names a rule that isn't registered.

## What it reconstructs

- **People's input.** Typed prompts, prompts typed while the agent was busy (and whether they were delivered at the next turn or absorbed mid-turn), slash commands, answers to questions, plan rejections and their feedback, rejected tool calls, and interruptions. Labels like correction, approval, and question are inferences from narrow rules; the correction rule uses the same patterns the weekly digest already uses. A message recorded with a peer or coordinator origin, or wrapped as sent by another session, an agent, or a schedule, is never counted as a prompt, whichever way it arrives. Neither is a turn a program sent: current Claude Code marks each user record with `turnOrigin`, `human` for one sent from the person's own session and `sdk` for one a script, the Agent SDK, a headless `claude -p` run, or another session sent. A `human` turn may be typed, pasted, or a task prompt the person started, which another session may have written, so it counts as theirs but isn't proof they typed it. A program's first turn is the session's starting instruction, as a `codex exec` run's is, a later one is a message to the session, and a slash command it sent is the program's, all recorded from that field. The agent's replies in a turn a program opened are replies to the program, not messages to the person, and stay so after a background task's notice opens a new turn. A message a program sent while the agent was busy is the program's in its queue record too. A session a program opened says so, on every page that names it. One relayed without such a wrapper or origin can't be told apart from typing. A prompt whose record carries no origin field, or one the engine doesn't recognize, is a person's only by a named rule, and so is a non-interactive Codex session's prompt, which a script may have written; the prompt count says when it includes one.
- **Sessions, agents, and delegation.** The main agent, each sub-agent with its type and description, who started whom (from the starting call's id), and when each finished (from the call's result or a completion notice). Codex child threads join their parent's session, and finish when their parent's log records them completing or holds their message back to it. Messages between sessions link when the sender's recorded message id matches the receiver's.
- **What started a program's run.** A Claude Code session whose first turn a program sent (`turnOrigin: "sdk"`), or a Codex session `codex exec` started, is linked to the step in another session that launched it when one fits, and the link says how it's known. It's recorded when the step names the run's session id: a shell call that runs `claude -p` (or `claude --print`) or `codex exec`, such as `claude -p --session-id <id>` or `--resume <id>`, or a Stop hook whose own record (its command, output or message) names it. It's derived when the call's command holds the first 120 characters of the run's opening instruction word for word (spaces collapsed, and only for an opening of 40 characters or more), or a Stop hook's record does; a call that holds the whole opening wins over one that holds only its start. A call that names a run's id is never matched to another run by its text, and a call that holds the same opening as two runs (a prompt something the logs don't show ran again later, say) links neither, while one command that holds several different openings, a loop, links each. It's inferred when it's the only `claude -p` call (`codex exec` for a Codex run) in the same folder in the 2 minutes before the run's first record, and no other run that started in that time fits it too. The step must have run before the run's first record (with 5 seconds of slack), and of several in one session that name it, the latest is linked, so a `--resume` sent after the run started is never its start. Steps in two sessions that fit, two calls in the folder in those 2 minutes, or one call that fits two runs link nothing, and the run says how many fit. A call that names another session's id or holds another run's opening never counts by its timing, a Stop hook never counts by its timing, and timing is never read across folders. Neither session can be in a display-only repository or outside the config. The link names a step; it doesn't join the two sessions into one thread, so each keeps its own replay. On the build machine's Claude Code logs from 30 September to 6 October 2026, read with its config, 162 runs a program started: 24 linked recorded, 46 derived, 17 inferred, 4 left ambiguous, and 71 with no launching step in the logs read (no `codex exec` run was in that window). In a survey of the 282 Claude Code logs written in those days, none of their 2,783 hook records named a run's id or held its opening.
- **Steps and their outcomes.** Each tool call with its recorded result, edits with line counts, test runs with parsed summaries, refusals by hooks and permission rules, API errors, compaction, and mode changes. A test command that was rejected, refused, or interrupted isn't counted as a test run, and a run counts as passed only when its summary shows no failure, no test file or suite failed to load, and the command's success was recorded. A clean summary from a command that failed, or whose success wasn't recorded (a Codex command that printed no exit code), is counted apart as unclear, because the record doesn't say which part failed, if any: the runner (a coverage gate, a crash after the summary) or another command in the line. Git then says whether each commit a session mentions exists, who authored it, and whether it reached the default branch, and which default-branch commit names each pull request and when it landed. Claude Code usually records its own commits and pull requests; Codex doesn't, so for Codex, and for any Claude Code command the harness didn't record, a commit or pull request is read from what the command printed, which is an inference and is tagged as one.
- **Time.** Spans of recorded activity, harness-recorded durations (labelled as the harness's own measurement), queued-message waits, calls still awaiting a result, open sub-agent spans, and quiet intervals (no records for a while, never called idle).

Replay is deterministic: the same logs and repository state always build byte-identical output, and the state at any moment has one answer. Seeking jumps to a time or steps forward and back one record at a time. Snapshots every 512 points keep a seek fast on a long history, and the tests prove a snapshot seek equals a full replay. The timeline and the summaries share one definition per counted thing, and a test checks that they agree on every shared count and on how each count is known. A count is never labelled more strongly than the weakest thing it counts, with one exception: a single session's counts include the records a resumed copy shared with it, placed there by the copy rule described under Duplicates, and that choice is marked on each record and on each commit and pull request it led to. So commit and pull-request counts at every level name the copy rule when it applied, while a session's other counts don't. Thread and day counts don't depend on the choice, since both copies sit in one thread.

## How the real example was used

I built and checked the model against one substantial real session on the build machine in this repository: a recorded span of about eight hours from its first record to its last, gaps included, with 13 typed prompts, four sub-agents, 446 tool calls, a call the harness later marked as never having a recorded result followed by a prompt asking it to continue, and three pull requests. The developer tool's `walk` command drilled from the week overview to that thread, its session, its busiest turn, one event of each kind, and the original log line behind each, then scrubbed the thread's time span. All 27 checks passed, and every sampled line re-read with a matching digest. That run stays on the machine; no session content is in this repository, and the tests use a synthetic corpus with the same record shapes.

What that session showed, as the engine printed it on 2 October 2026, before the independent review's fixes: 13 prompts (recorded), 1 approval (inferred), 1 interruption (the harness's record that a call's result was never written), 4 sub-agents with recorded parents (3 finished by a notice, 1 by its call's result), 64 edits (recorded) across 29 files (derived), 41 test runs (inferred; 28 all passed and 9 with failures, printed then as derived and now inferred, and 4 with no parsed summary, so missing), 1 call refused by a hook, 2 commits that git confirms exist and were authored by me (neither on the default branch itself), and 3 pull requests that a default-branch commit's subject named (printed then as recorded, now inferred). Those fixes changed rules this paragraph depends on, among them: messages relayed from other sessions or schedules are no longer prompts; a summary showing a test file or suite that failed to load now counts as a failure, and a clean summary from a failed command is now unclear rather than passed; after a quiet commit (`git commit -q`, which prints no commit id) the id is read only from a log that prints HEAD (the commit just made) first; and a pull request can now also match through a merge's subject. None of these numbers or their labels was re-measured under the new rules, so any of them may have moved.

### Codex

Codex has written its logs in two formats. In the older one, each shell command and each patch is its own tool call. Since August 2026 (every version from 0.144.6 to 0.159.2 on the build machine), each step is an `exec` program: a small JavaScript program Codex's `exec` tool runs to call its other tools (not the non-interactive `codex exec` mode). A program calls `tools.exec_command` to run a command and `tools.apply_patch` to change files, and prints what it wants the model to see. Codex 0.154 and later also write an `item_completed` record for each command a program ran (with the command line, exit code and output) and for each file it changed (with each file's diff); the 0.144 command line often doesn't. The engine reads both formats, and a program's steps come out as the same kinds of event a Claude Code session's do:

- **Recorded.** Each command and file change the harness recorded is a step of its own, with its exit code (ok or error), its files and line counts, its test summary, and any commit or pull request its output names. It's tied to the program that ran it, and the program's call is the step's first reference.
- **Derived.** A tool call the program's text makes that no record covers is read from that text: the command or patch when it's spelled out in full (a string, or a name given one once), with its exit code only when the program printed the command's own result. This happens only when the text leaves no doubt: every call runs once, in order, each awaited before the next, with no loop, branch, function, error handling or parallel call anywhere in the program. A patch in such a program that ran to the end applied; one the output says failed is an error, and the calls after it never ran. A call with no recorded outcome has its result missing, never guessed.
- **Shown, not read.** Any other program (a loop, a command built at run time, a failure the error doesn't pin on one call, or one running beside another program when a record can't be tied to either) stays one step, shown as written, beside whatever the harness recorded. A program's own failure (its output says "Script failed") is that step's recorded error.

Four more things a Codex log holds come out the way a Claude Code session's do:

- **A child thread's hand-back.** Current Codex writes, in the parent's log, a record each time one of its child threads starts, is sent a message, completes, or is interrupted (`SubAgentActivity`). A completion or an interruption is a notification event tied to the child. A child thread has handed back when its parent's log records it completing, or, failing that, holds a message from it to the parent. A child that was stopped lost nothing, so it's marked stopped, not missing: when the parent sent it an `interrupt_agent` call naming its task (after it started), when the parent's log records it interrupted, or when the child's own last record is an interruption. A parent that recorded the child starting and none of these marks the hand-back missing; a parent that recorded nothing about the child (older versions write no such records) leaves it unknown, never missing. On the build machine's Codex-heavy week (15 to 21 September 2026), 189 child threads had a recorded spawn: 175 handed back by a completion record, 11 by a message only, 1 was stopped (its own log ends on an interruption), and 2 have no hand-back. These records don't count toward how the parent's own session ended, since a parent records a child finishing whether or not it was still working.
- **Plan mode.** Codex's plan mode is a collaboration mode, recorded in each turn's settings (`turn_context`). A turn whose mode differs from the turn before is a mode event; a first turn in the default mode isn't. Codex writes a turn's settings after its start record and before its prompt (470 times that week), after the prompt (274) or after a tool call (81); the event belongs to the turn the settings govern, so one written after a turn ended waits for the next prompt. The value `plan` is taken from the installed Codex binary's own strings: none of the 13,019 turns on the build machine used it.
- **Titles.** Codex keeps the name each thread was given in `session_index.jsonl` beside its `sessions` and `archived_sessions` folders, one line per name; the latest line for a thread wins. A session's title comes from there, redacted and cut to 160 characters like any title; a display-only session has none. 25 of that week's 62 Codex sessions have one.
- **Branches.** The branch a thread started on, as Codex records it, links the session to that branch (`session-start`), so a branch lookup finds Codex sessions as it finds Claude Code ones. Display-only sessions add no branch link.

A command left running in the background is recorded when it ends, after its program's output; that record replaces the step read from the program's text. A forked thread's file opens with a restamped copy of its parent's file-change records, and the copies within its first 2 seconds aren't read as its own work. While an older-format shell call is waiting for its output, a command record is its echo and isn't read twice.

### Git

Commits the harness recorded, or that a successful commit command printed (an inference), are looked up in the session's own repository. A commit id counts as printed by the commit only from git's own summary line, or, after a quiet commit, from a `git log` or `git show` of the same repository joined to it by `&&` that prints HEAD first (no other revision, path, or ordering option), when nothing earlier in the line prints. When several sessions name one commit, the harness's own record wins over printed output. Pull requests are matched by number only when the record names the same repository as the configured repo's remote. Git has no record of pull requests, so a pull request counts as landed when a default-branch commit by a configured identity names it in its own subject, or reached the default branch in a merge whose subject names it (whoever authored the merge). The earliest landing is cited, so a later commit that names the same number never moves it; within one landing, a commit whose own subject names it is preferred. The description says which of the two it was, and the match is tagged as an inference. A configured path git can't read is reported as unreadable, never as a missing commit or an unlanded pull request. Display-role repositories and sessions outside the configured repos are never passed to git.

## Messy records

- **Clocks.** Event time is the record's own timestamp. The survey found 87,486 records stamped earlier than the latest stamp above them in the same file, by up to 2.9 days. Of the 59,816 such steps of more than a minute in session files, at least 92% (55,138) came right after a pull-request link or queue record had set that latest stamp, which fits those records being stamped out of band and resumed sessions copying older records below fresh ones; the survey can't say which record holds the wrong time. So the engine doesn't force time forward, and pull-request links and queue records never set a session's span or quiet intervals. Only recorded cause and effect constrains time: a result can't precede its call, and a sub-agent can't act before its starting call. A violation is kept as an anomaly with its size, and only the later event moves.
- **Duplicates.** 109 session files begin with a record that appears in an earlier file (a resume or fork copies history and keeps the record ids). Each copied record is counted once, and the two sessions join one thread. Which copy is the original is a named rule (the one whose file ends first), and every kept record a copy shared carries that rule as an inference. A link, a completion notice, or a hand-off a copy repeats is counted once, and a copied first prompt doesn't make the copy a hand-off target. When the copy recorded a call's result that the original never did, the result, and everything it links to, moves to the kept call. A Claude Code reply split across several records is one message. A Codex turn written in two formats is one turn.
- **Incomplete sessions.** 216 transcripts hold at least one call with no result later in the same file. The engine never says a session "ended": it reports what the last record was, and a call with no result stays open on the timeline, marked as never recorded. A cut-off last line is counted and skipped.
- **Interruptions.** A person pressing stop, a turn limit, a Codex turn the harness aborted, and the harness's later note that a call's result was never written are separate interrupt events. Codex records its own reason word, not who stopped the turn, so the engine doesn't say who did.
- **Privacy.** Every string is redacted before it reaches an event, including the keys of records that key values by free text. File paths keep only directory shape and extension. Sessions outside the configured repos are left out; with scope `all`, they and display-role sessions appear as skeletons that keep the kind of each step, its time, its tool category, the harness's own tool name (never an MCP server's or a custom tool's), whether it succeeded, and its exit code and recorded duration; never text, paths, commit ids, pull-request numbers, names, custom agent types, model names, or line and test counts. Drilling into one shows the record's top-level shape only. Repository labels are redacted like any other string. A commit id the engine itself records (in an event's facts or a lookup row) is kept as it is, even one made only of digits, which the redactor would otherwise read as an account number. Everywhere else, including a raw record read back and a goal's own text, a long run of digits is still redacted, whatever its key is called. In a raw record read back, a value whose own key names a secret (`"password"`, `"x-api-key"`, `"dbPassword"`) is hidden whole, as `[redacted:secret]`, and so is one under a dotted key that names a secret, such as `"api.key"` or `"db.password"`. An answer keyed by the question's text keeps its answer. In any text, a command-line option named for a secret hides its value, and that includes a name with dots in it: `--docs.token`, `--api.key` and `-Docs.Token` are read the way `--docs-token`, `--api-key` and `-DocsToken` are. A dotted name that doesn't name a secret, such as `--config.file`, keeps its value. A Java or Gradle property set on a command line is read by its own name, the part after `-D` or `-P`: `-Dapi.key=…` and `-Psigning.password=…` hide their values, and `-Dfile.encoding=UTF-8`, `-Dlog.level=debug` and `-DskipTests` stay readable. A dotted key that isn't an option, such as `api.key=…` or `secret.key: …`, hides its value when the secret's name runs across the dot, the way `api_key` does. That holds inside a quoted note whose closing quote is missing, too. A dot that only follows a secret-sounding word, as in `auth.ts:42` or `password.length === 0`, is a file name or code and reads as before. A secret's value that opens with a single quote and never closes it on its line, such as `password: '…`, is hidden as well. These three spellings are read last, in a pass over text the other rules have already finished with. That pass only adds placeholders: it never reads, moves or removes one that's already there, and it changes nothing else. So it can't bring back anything the other rules hid. One more step reads the text as it was written, before any placeholder went in, for two things the other rules leave. The first is a secret field whose value is itself a name, so that the real value comes after it: `api_key=token: …`, `password="token": "…"`, or a dotted key at the end of a quoted value, as in `token: "Ab3d, api.key: "…"`. The inner name has to name a secret, or be a single quoted word. The second is a key such as `apiKey` that sits on its own line after an ordinary `name=`, with its `=…` on the next line. What that step finds is hidden in the finished text in addition to everything already hidden there: it swaps more of the shown text for a placeholder and touches nothing else. It can hide a harmless word, the way the other rules can: in `auth: token: required`, `required` goes. Nothing is sent anywhere.
- **Excerpts.** The engine keeps a short excerpt of long text: the first 600 characters of a prompt, 400 of a message, 300 of a command, 160 of a description or an answer, 120 of a search query, 80 of a branch, a name, a search pattern or a message's recipient, and fewer for the harness's own words, such as a status, a hook's name or a mode (60, 40, 30 or 20). A raw record read back keeps up to 2,000 characters of each string. An excerpt is made in three steps: each run of spaces, tabs and line breaks becomes one space, private words are hidden in the whole of that text, and only then is it cut. So a private word that crosses the cut is hidden whole. Cutting first, as the engine used to, left the word's start on screen, because the redactor no longer recognized what was left of it. When the cut would land inside a placeholder such as `[redacted:term]`, it moves back to just before it. What's left is read by the redactor again, because the redactor spares some longer forms it hides once they're cut, such as a configured name inside a longer word or a key id with a letter glued on, and cutting first hid them too. Where nothing hidden crosses the cut, an excerpt reads exactly as it did when the engine cut first, character for character, even when something earlier in the text was hidden. Three kinds of text read the whole before taking a part of it, so they can change where they used to show something:
  - a first-line excerpt, such as the reason a hook gave for refusing a step, collapses each line's whitespace and hides private words in all the lines together before it takes the first, so a name, or a secret's value, broken across the line break is hidden too. It shows nothing of the next line but the placeholder that took the break, and where nothing hidden takes the break, it reads as before;
  - a goal citation made of words (`session:` followed by words) is an excerpt as well, so repeated spaces in it now read as one;
  - a raw record read back keeps its line breaks, but the redactor's rules for a secret field read one line at a time, so each string is also read with its whitespace collapsed, and when that hides more (a password on the line after `password:`), the record shows the collapsed text.

  On the demo week and the test corpus, with and without goals, scope `all` and `privateText`, every history, record, event, view, timeline moment, goal and lookup reads byte for byte as it did before this change: 7,912 comparisons, no difference. Nothing hidden crosses the length the engine cuts each field to in those logs, so that check covers only the text that didn't change; the tests that put a private word across every cut length cover the text that did.
- **Hidden sessions, redacted.** By default, sessions outside the configured repos (with scope `all`) and sessions in display-role repos are skeletons. With the `hiddenSessions: 'redacted'` option they keep their content instead: prompts, messages, commands, titles, agent types and models, and a raw record read back whole rather than its shape. Every string passes the full redactor, the same one every other session's text passes, so configured names and terms, email addresses, home folders (`C:\Users\…`, `/home/…`, `/Users/…`, `~/…` and `/root/…`), session ids and secrets stay hidden. Codex's agent addresses (`/root`, `/root/wide_fixtures`) stay readable where they come from its agent fields. Other folders show as they do in any session's text, among them a project folder outside the home folder. Commit ids the log recorded show, as they do wherever the full redactor runs. The hashes of a raw path or prompt that lookup by file reads in other sessions are dropped, since these sessions are never looked up and a hash could confirm a guess. What doesn't change: these sessions still add nothing to links, goal membership or lookup, they're never scanned for goal ids, and display-role repos are never read by git. A test records every process the engine starts while it builds the history and answers lookups, and checks that none runs git in a display-role repo and that the git calls are exactly the default build's. The history says so (`hiddenSessions: 'redacted'`) and, unlike one built with `privateText`, it can be turned into JSON, since nothing in it is unredacted. Without the option, or with `'skeleton'`, the history is byte for byte what it was. With `privateText` as well, `privateText` decides what shows.
- **Token counts, numbers only.** With the `usage` option the history gains `usage.calls`: one entry for each model call the log records token counts for, with its session, agent, source file, tool (`claude-code` or `codex`), line numbers, time, and four token counts (input, cache writes, cache reads, output), plus, where Claude Code records it, how long the call's cache writes last (`ttl`: `5m` or `1h`, from its split of the writes; `1h` when a call has both). It holds numbers and ids, never text. A Claude Code call is one assistant message; a message whose content blocks were written as several records is one call, at the largest value of each count, and a message a resumed or forked session copied into its own file is counted once, in the earliest-ending file, the same rule the engine uses for copied events. A Codex call is a token-count record that carries the call's own counts and whose running total differs from the record before it. An unchanged total is no new call: it repeats the last call's counts, or right after a compaction holds Codex's estimate of the shortened context, as does a record with no input and no output. A lower total is Codex starting its count again at a turn. A Codex sub-agent's file (one forked from another thread) opens with a copy of its parent's history. In a file written as the sub-agent ran, a token count within 2 seconds of the file's first record is part of that copy and isn't the sub-agent's call (measured on 601 such files: the copies end within 353 ms, and the first call of the sub-agent's own comes at 3.2 seconds). Some Codex files carry one time on every record (on the machine this was built on, the thread's start: the spawn, for a sub-agent), and time can't separate the copy there. Copies of the parent's calls keep its counts as written, so a Codex call several files of one fork family hold (the same running total and the same counts) is counted once, in the file the fewest forks from the family's first thread, which is the parent's, then the earliest-ending. Unrelated sessions don't share calls, even with the same counts. When the parent's file isn't read, for example because it ended before the window, a copy past the sub-agent's opening, or the whole copy in a file whose records carry one time, counts under the sub-agent, at the time it was copied; the opening copy of a sub-agent written as it ran still doesn't count. A parent's calls from before its own file begins (a parent file that starts partway through its thread) aren't counted from a sub-agent's opening copy, except once, under the sub-agent, when only a sub-agent whose records carry one time holds them (measured on that machine: about 0.8% of Codex tokens left out this way). Codex's input includes the cached part, read as cache reads; a cache-write count is taken to sit inside the input the same way, which is assumed, since every one on the machine this was built on reads 0. Reasoning is added to output when the record's own total counts it on top. The line number Codex records where a sub-agent's own history starts (`subagent_history_start_ordinal`) isn't used: in 770 of the 959 sub-agent files on that machine it points past the file's end. What isn't counted: a call the log keeps no counts for, such as the summary Claude Code writes when it compacts a conversation, and a Codex total that moves without the call's own counts. The calls cover every file the history read, so a sum for the window filters them by `t`, with two caveats: copies counted under a sub-agent because their parent's file isn't read, above, and Codex files that carry one time on every record, whose calls are all dated at the thread's start, before they ran. Skeleton sessions get none. Without the option the history is byte for byte what it was. It's there for the local page's problem checks.
- **Raw text for checks in the same process.** With the `keepRaw` option each tool call keeps its raw input (for Codex: its parsed arguments, a custom tool's input, a local shell action, and arguments that aren't valid JSON as written), each `message` the agent wrote and each `prompt` its full text (not `agent-message` events), and a call whose result is an error the start of its error text (up to 2,000 characters; not a call that was interrupted, rejected or refused), on a field named `_raw` that isn't enumerable; the history's own `_raw.cwdOfSource` holds each readable file's working folder, so a check can tell an edit inside the session's folder from one outside it, `_raw.fileOfSource` holds each readable file's path, so the Problems page can read a tagged test session again (lib/problems/fix-tests.mjs), and `_raw.repoOfPath(path)` names the configured repository a path sits in (its redacted label and role), read from the configured folders alone, never from git. A Claude Code shell call also keeps the folder its log line recorded (`_lineCwd`), since a `cd` in an earlier call moves it. JSON, spreads and `Object.keys` leave it out, so nothing built from the history carries it unless code reads `_raw` by name, and the history serializes exactly as without the option. Separately from `keepRaw`, every Claude Code event outside a private session keeps the branch its log line recorded (`_lineBranch`), also not enumerable and never serialized or saved. A Codex sub-agent's copy of its parent's history is read as the sub-agent's events, as it is without the option, so those events keep raw text too. Sessions outside the configured repos and in display-role repos never get it, not even with `hiddenSessions: 'redacted'` or `privateText`, where they keep their other content. No planned check reads them, and under `hiddenSessions: 'redacted'` a check that kept a fingerprint of their raw text could confirm a guess, the reason these sessions drop their hashes there. When a resumed copy holds the error result the original never recorded, the error text moves to the kept call with it. It's for checks that classify text and compare inputs in memory and keep only booleans, counts and fingerprints, such as the local page's problem checks.
- **Progress updates, by position.** On Claude Opus 5.5 and Fable 5.1, the updates the agent writes to the person between tool calls arrive as `thinking` blocks, and no field marks which block is one. With the `updates` option, a thinking block becomes an `update` event when its text isn't empty, it's the last thinking block of its model response (the records that share one `message.id`, since Claude Code writes each block as a record of its own), the very next block of that response is a tool call, and the recorded model id starts with `claude-opus-5-5` or `claude-fable-5-1`. That's the `updates.position` rule, so every update is inferred: a reasoning summary can sit in the same place. Two thinking blocks before one tool call give one update, the second. Every other thinking block, an encrypted one, a signature, and any thinking block in a skeleton session stay unread, and the coverage tally counts the updates shown and the thinking blocks still excluded. An update's text is redacted and cut like a message's, and `keepRaw` keeps its full text in memory for the checks. Spans, quiet intervals and end states leave updates out, so they read as without the option. Only `honestweek view` asks for it. Without it the history is byte for byte what it was, and the rule isn't in its rules table.
- **Private text, on your own screen only.** A page served from your own machine can ask for a history built with the `privateText` option. Then names, folders, email addresses, session ids and long numbers show as written, and sessions outside the configured repos or in display-role ones show their content too. Secrets stay hidden, by the same rules the full redactor uses: known API-key and token shapes, JWTs, long random-looking tokens, and the value of a sensitive field: a key naming a password, token, secret, API key, cookie, signature or authorization, in spellings from `API_KEY=`, `x-api-key:` and `client_secret` to `dbPassword`, `authtoken`, `PGPASSWORD` and `MYSQL_PWD`. It covers it whether written with `=`, `:`, `:=`, `==` or `===`, typed (`password: string = …`), as a quoted JSON string at any level of escaping, after a `--flag` or `-Parameter`, or as a JSON value read back from a record. It also covers Authorization and Cookie headers, Bearer and Basic credentials, the password in a web address or after curl's `-u`, and a PowerShell SecureString. A password line and a header hide to the end of the line, or to the next `key:` on it: the engine joins an event's excerpt into one line, and a secret under the next key is then read on its own. Other `key: value` text hides only the value, so prose like "Auth: users get logged out" stays readable. What it shows that the full redactor hides as a secret: a bare session id (UUID), and a long run made only of words, such as a folder name, branch name or web address (`quiet-river-20c28a`). A passphrase made of dictionary words with nothing naming it would show too. Like the full redactor, it shows hex up to 40 characters, so a short hex key looks like a commit id, and it can't recognize a secret with nothing around it to name it, such as a password glued to `mysql -p` or a plural `tokens` list. What it changes is only the text you see: which sessions are linked, scanned for goal ids, or sent to git stays exactly as without it, and display-role repos are still never read by git. The history says so (`privateText: true`) and refuses to be turned into JSON whole. Only `honestweek view` asks for one, and only while its Show private text switch is on: a test fails if any file under `bin`, `lib` or `tools` other than the engine, the redactor, and the page's data, search-everywhere and leak-counter files names the option.
- **Size.** Files are streamed, and a record over 8 MB is skipped and reported. A file's first and last timestamps are found by reading as far as needed, since one record can be larger than any fixed window (on the build machine, in a separate survey run from the one above, 20 of 3,897 session files had their first timestamp past their first 64 KB). Files not written since two days before the window are skipped without opening: a log is appended as work happens, so it can't hold a later record. Modification time is never used as evidence of when work happened, because 937 files on the build machine share one modification date from a bulk copy. On the real machine a two-day window built in under 3 seconds, measured before excerpts were redacted whole. That costs more where text is long: on the build machine, a made-up 22 MB session made mostly of long prompts, messages and commands built in about 17 seconds, against about 6 before, and one made mostly of tool output built in the same half second as before. A synthetic 12,000-call session builds and answers 2,000 seeks within the test's limits. Finding when commits landed walks each configured repository's whole default branch once, with one git call per merge commit, so that cost grows with a repository's merge history, not with the window.

## What it can't reconstruct yet

- **Working time.** Logs record moments, not effort. Gaps between records aren't working or idle time, so the engine reports recorded spans, the harness's own durations, and quiet intervals, never active hours.
- **Why.** A reason exists only where a person or agent wrote one in a prompt or message. Private model reasoning is excluded by design, so a decision without a written reason shows no reason.
- **Approvals that weren't refusals.** In normal permission mode, a tool call the person approved looks the same as one a rule allowed. Rejections are recorded; approvals aren't. Codex records its approval policy for each turn (12,957 of the build machine's turns say `never`, 246 `on-request`), but no request for approval and no answer to one: none of its 3,539 rollouts holds such a record.
- **Who edited a file outside the agent.** The harness notes the change, not whether the person or another program made it.
- **Sub-agents whose starting call isn't in the logs read.** 968 sub-agent metadata files name a starting call that isn't an Agent or Task call in their parent file. The engine links any call id it finds, so some of these do link; how many stay unlinked wasn't measured. The rest appear with the missing link marked.
- **Several inline sub-agents in older logs.** Before sub-agents got their own files, their records sat inside the session file without an id, so they collapse into one marked agent that may stand for several.
- **Which copy of a forked session is the original** when the original kept going after the fork: the rule picks the file that ends first, so the shared records can land on the fork, each tagged with the rule.
- **Which repository a commit belongs to** when a command changed directory first. The engine says the commit isn't in the session's repository rather than guessing.
- **Commits a quiet command never printed.** When the harness didn't record a commit and the command printed no commit id, git isn't asked about it.
- **Pull-request reviews and CI.** The engine reads no network service, so review comments, approvals on GitHub, and CI results are absent. It knows what the session recorded and what local git has.
- **Clock differences between machines.** Skew is detected only along recorded cause and effect inside the logs it reads.
- **A program's run started from outside any session.** A script, a scheduled task or a server process that runs `claude -p` or `codex exec` writes no session log, so its runs say only that a program started them. So does a run whose opening came from a file or a pipe in another folder, or one whose launch quoted the text differently from how the run recorded it.
- **Hand-offs without a recorded id.** A session started from another's task suggestion is linked only when its first prompt matches the suggestion exactly, and that link is an inference kept outside the thread. Hand-off documents written by one session and read by another aren't linked yet.
- **Abandoned approaches** beyond what's explicit: a rejected plan, a refused or rejected call, a revert command, a stopped background task, an interruption, or a correction. The engine doesn't guess that a sequence of steps was an abandoned attempt.
- **Plan lists over time.** To-do and task updates are captured on each call, but not yet folded into a plan timeline of their own.
- **Codex edits made inside shell scripts,** which can't be told apart from other shell work, and, when Codex wrote no record of them, the calls inside an `exec` program whose text doesn't settle what ran (a loop, a command built from pieces, a failure the error doesn't pin on one call). Their program is shown as one step instead. Codex also runs hooks without recording them, so a Codex session never shows a hook, and the problem checks don't treat the missing hook record as evidence there.
- **Anything older than the retention window.** Claude Code deletes transcripts after its cleanup period, so nothing before the oldest file exists to reconstruct, unless `view` saved it first (next section).
- **Claude desktop local-agent sessions,** which the miner reads, aren't read here yet.

## Sessions saved by an earlier run

With `saveResults` on, `view` saves each session the engine built, and a later build can take a session back that it didn't read from a log (`saved`): because its log is gone, or, named in `reuse`, because its logs haven't changed since it was saved, so reading them again would give the same thing. A reused session's files stay known, so its steps are still checked against their log lines, and it carries no saved label. One that was running in the two minutes before a session a program started (one this build reads) is read from its log after all, since a launch is matched by the launching command's text, which isn't saved. It comes back as if it had been read: its steps, agents, links, token counts, and the joins that tie it to other sessions, goals and git. Threads, goals, pull-request and commit lookups, the timelines and the git outcomes (read from git again) work on it as on any other session, and a week given back whole from saved sessions has the same sessions, threads, steps, agents, links, goals, token counts and turns as the week built from its logs, which a test checks on the demo week. Anomalies about a saved session's steps aren't saved, and the checks don't run on it again: Problems shows the findings saved with it. Its session record says `saved: { at, by, log }`. What it can't do again:

- **Check a step against its log line.** `record()` says the log is gone and checks nothing; each step keeps the evidence word it had.
- **Be matched to a launch by its command's text.** A session a saved session launched is linked only by a launch link saved with the launched session; a command's text isn't saved.
- **Show private text, or lookups by file or branch.** Neither the text nor the paths and branch names are saved (branch names only redacted), so Show private text shows it redacted and those lookups don't reach it. Search everywhere reads logs, so it doesn't either.

Nothing raw is saved: an event's in-memory fields (`_raw`, `_command`, `_workdir`, `_lineCwd`, `_lineBranch`) are left out, record ids, message ids and token call ids are kept as hashes, and every string is redacted when it's saved and again when it comes back. With saved sessions in a build, the ids a fresh session shares with one (a resumed copy's records, a message's id, a token call's id) are compared as hashes too, so a resumed copy still collapses into its original. Without `saved`, nothing changes.

## Goals and lookup: reading the history backwards

The timeline answers "what did this session do?". Two additions answer the reverse: "which sessions did this goal's work?" and "which sessions worked on this pull request, commit, file, or branch?". Both use the same four evidence levels, so every answer says how it's known, and both leave out sessions outside the configured repositories and in display-role ones.

### Goal membership

A **goal record** is my own list of goals, kept as JSON. Each goal has an id and a title, and can carry a state and four lists of notes: where it came from (`source`), `observations`, `results`, and `decisions`. Beside the list sits the record's write log (`events`): one **entry** per change to the record, each with an id the writer chose, the goal it belongs to, its type (`goal.create` for the entry that created the goal), and `at`, the time the record accepted it.

```json
{
  "goals": [{ "id": "g-widget", "title": "Ship the widget parser", "state": "active",
              "source": { "pr": "https://github.com/example/your-project/pull/7" },
              "observations": [{ "text": "Started in session:0a0a0a0a-1111-4111-8111-00000000000a" }] }],
  "events": [{ "eventId": "ev-0001", "goalId": "g-widget", "type": "goal.create", "at": "2024-06-11T21:41:30Z" }]
}
```

Given a goal record, the engine lists each goal's **members**: the sessions that did some of its work, as far as the records show. Each member carries its **joins**, the reasons it counts, and each join has an evidence level. A **citation** is a reference inside the goal's own notes: a pull-request link, `your-project#7`, `session:` followed by a session's id, `commit:` followed by a commit id, or a bare 40-character commit id. A session's id is the one its harness gave it: a Claude Code session file's name, or a Codex thread id.

| Join | Evidence | What it means | Example |
| --- | --- | --- | --- |
| cited-session | recorded | The goal record names the session by its id. | An observation says `session:0a0a0a0a-…`. |
| cited-pr | recorded | The session's harness recorded a link to, or a git fact about, a pull request the goal cites, in the same repository. It's inferred, under the existing `shell.gh-pr-output` rule, when the harness didn't record the pull request and the link was read from what a `gh pr create` command printed, in a Claude Code or a Codex session. | The goal's source is pull request 7 of your-project, and the session recorded a link to it. |
| cited-commit | recorded or inferred | The harness recorded a commit the goal cites. It's inferred, under `shell.git-commit-output`, when the commit was read from what a commit command printed. | The goal says `commit:00700b7dc502`, and the session's commit call recorded that commit. |
| wrote-entry | derived | A tool call's input carried one of the goal's entry ids, and the record accepted that entry while the call ran. A call a person rejected, a rule refused, or that was interrupted never counts. | A call began at 21:42 with `--event ev-0002` in its command, its result was recorded at 21:43, and the record accepted ev-0002 at 21:42:30. |
| created-goal | derived | The same rule, for the entry that created the goal, kept apart so a view can show creation differently from work. | The entry is `goal.create`. |
| command-on-pr | inferred (`pr.gh-command`) | A `gh pr` command acted on a pull request the goal cites, in the repository the command names or, when it names none, the session's own. | `gh pr view 7 --json reviews` |
| prompt-names-goal | inferred (`goal.prompt-names-id`) | A prompt names the goal id as a whole word. A longer id that contains it doesn't count, and a dot followed by a letter or digit is part of an id, so `g.1` isn't found in `g.1.2`. | "Now carry on with g-widget." |

A session that only mentions a pull request or a commit in a prompt or a message never joins: a mention isn't work.

**Which repository a pull request is in.** A pull request is a number in a repository, and a repository is an owner and a name (`example/your-project`). When both the citation and the session's record name an owner, the owners must match as well as the name and the number. A citation that names no owner (`your-project#7`) matches by name, but when the sessions it matches name more than one owner, which repository the record meant is open: each of those joins is marked ambiguous with the number of owners, rather than the engine picking one. The other way round is open too: when a citation names an owner and a session's pointer doesn't (its repository's origin remote couldn't be read, or git wasn't read, so only the configured label names it), that join is marked ambiguous as well.

**A member's level.** A member's own level is the strongest of its joins, where an ambiguous join ranks below every unambiguous one, inferred included. When a member's strongest join is ambiguous, the member is marked ambiguous too. Members are listed in the order of their first record. Whatever in the goal record didn't match is listed too, with the reason: a citation no readable session points at, `session:` followed by words instead of an id (the engine doesn't guess which session that meant), or an entry no call wrote.

**Why a write needs the time to match.** An entry id in a call's input isn't enough on its own. A session that read or searched the goal record would carry the same ids, and would count as having written them. So a call counts as writing an entry only when the record accepted the entry between the call's own recorded time and its recorded result's time, both as the log wrote them. A call with no recorded result never qualifies, and neither does one a person rejected, a rule refused, or that was interrupted. When calls in more than one session carried the same entry id while the record accepted it, each of those joins is marked ambiguous with the number of candidate sessions, rather than the engine picking one. The tests prove all three cases on a made-up session that writes entries, then searches the record for them later.

**Why the scan happens while parsing.** The engine keeps only the first 600 characters of a prompt and a clipped copy of each command, and a goal id or entry id can sit past either cut. So the ids are looked for while each log line is parsed, in the full text: entry ids in a tool call's whole input (never its result), goal ids in a prompt's whole text. Sessions outside the configured repositories and in display-role ones are never scanned. Without a goal record nothing is scanned and the history's JSON is byte for byte what it was. The three new rules label joins and lookup results, never events, so the history's table of rules names them only when a goal record was given, and each lookup result carries the description of every rule it names.

### Lookup

Lookup takes what I'd type, such as `#64`, `your-project#64`, a pull-request link, a commit id, a file path, or a branch name, and lists the readable sessions that point at it, strongest evidence first, each with how it points. When a goal record was given, it also names the goals those sessions are members of.

- **A pull request** is found through the harness's own link records and git facts (recorded), links read from what a `gh pr create` printed (inferred), git's record of the default-branch commit that names it (inferred, as it is everywhere in the engine), and `gh pr` commands that act on it (inferred, `pr.gh-command`). Without a repository name, a number matches in any repository. With a name and an owner (`example/your-project#7`), a pointer that also names an owner must name the same one. With a name and no owner (`your-project#7`), a pointer matches by name, and when the matches name more than one owner, each is marked ambiguous and a note says so. With an owner, a pointer that names no owner is marked ambiguous, also with a note. Every pull-request pointer in the answer names the repository it's in (owner and name, or which part is unknown), so pull request 7 of one repository never reads as pull request 7 of another.
- **A `gh pr` command** counts only when its subcommand takes a pull request (not `create`, `list`, or `status`) and the number or the pull request's link is its own argument. A link anywhere else in the line, such as after `echo`, doesn't count. The repository is the one the link names, else `--repo` (`-R`), else `GH_REPO` (set with `GH_REPO=` or PowerShell's `$env:GH_REPO`), else the session's own. With none of those named, a command after a `cd` in the same line, or a Codex call whose working folder is outside the session's repository, names no repository and doesn't count. A call a person rejected, a rule refused, or that was interrupted never counts.
- **A commit** is found by any prefix of 7 characters or more, through commits the harness recorded (recorded), commits a session named that git confirms exist (recorded when the harness recorded them, inferred when they were read from printed output), and pull requests that landed as that commit (inferred). When the commit's subject ends in `(#N)`, the shape GitHub writes for a squash merge, the sessions behind pull request N are included too, inferred under `pr.squash-subject`. Git reads that subject only in configured repositories that aren't display-role.
- **A file** is harder, because the engine never keeps a file's full path, only a fingerprint of it, and the same file in two **worktrees** (separate folders holding checkouts of one repository) has two different fingerprints. So a path is tried under each checkout of a repository: the configured folder and each of its worktrees, as git lists them and as the repository's own records name them. A session's working folder is never one of those roots, since it can be a subfolder. An absolute path belongs to the one repository whose checkout holds it, and only that repository's checkouts are searched. A relative path is tried in each configured repository, and the answer lists what it found per repository, never merged. It says how many folders were tried, never which.
- **A branch** is found through the harness's records of a push, a branch operation, the branch of a worktree a session entered, and the branch a Codex session started on (all recorded).

What lookup can't find:

- a file edited from a worktree that's since been deleted, when that folder is no longer listed by git and wasn't any session's working folder;
- a commit a quiet command never printed and the harness didn't record;
- a pull request named only in a prompt, a message, a commit message, or a comment body: free text is never read as work;
- a `gh pr` command that changed directory first without naming its repository, since which repository it acted on isn't recorded;
- a `cd` in an earlier call: the engine reads each command line on its own, so a `gh pr` command after a separate call that changed directory is still read as acting on the session's repository;
- anything in a session outside the configured repositories or in a display-role one;
- reviews, approvals, and CI on GitHub, since nothing here reads the network.

A session's repository is named by its origin remote (owner and name) when git is read, and by its configured label (a name with no owner) otherwise.

### Phrase search

Words that aren't a reference are matched against the history too, the same way for the view page's Find and for `honestweek find`: goal titles and ids that hold every word, titles of sessions in configured repositories that hold every word, branch names that hold the text, and up to 20 prompts that share any of the words, most shared first, then newest. Words in a title, a branch name or a prompt are recorded there; ranking prompts by how many they share is a named rule's reading (`view.shared-words`), and so is "similar prompts" (`view.similar-prompt`). A display-only or outside session never joins these matches. "Search everywhere" then reads the prompts and titles of every session on the machine in the window again from the logs, display-only and outside ones included, and redacts each excerpt whole before cutting it.

## Trying it

The published commands answer from the package alone, on the made-up demo week:

```bash
honestweek find --demo '#12'
honestweek find --demo date filter
honestweek replay --demo cc-hccfcndehggh --at 2025-03-10T09:30:00Z
honestweek problems --demo
honestweek goals --demo
```

From a clone of this repository, a developer tool prints the history level by level (it isn't in the published package):

```bash
node tools/replay-inspect.mjs --config honestweek.config.json --from 2024-06-10 --to 2024-06-16 walk
```

`overview`, `thread`, `session`, `turn`, `event`, and `record` print one level each; `at` and `step` scrub time; `coverage` lists every record type seen in the run and how it was handled; `goals`, `goal <id>`, and `lookup <text>` read the history backwards (the first two need `--goals <file>`); `--json` prints the same data as JSON. The tool redacts everything it prints and writes nothing to disk.

To see goals and lookup without any logs of my own, `--demo` runs the commands on the made-up logs, git repository, and goal record the tests use. It builds them in a temporary folder and deletes it afterwards, so it needs only a clone and git:

```bash
node tools/replay-inspect.mjs --demo goals
node tools/replay-inspect.mjs --demo goal g-widget
node tools/replay-inspect.mjs --demo lookup '#7'
node tools/replay-inspect.mjs --demo lookup lib/widget.mjs
```

On my own logs, the same commands take a goal record file:

```bash
node tools/replay-inspect.mjs --config honestweek.config.json --from 2024-06-10 --to 2024-06-16 --goals goals.json goals
```

## Implementation detail

- Saved sessions: `lib/replay/saved-sessions.mjs` (`exportSession`, `savedAsParsed`, `restoreSaved`). `buildWorkHistory` takes `saved` (sessions to give back) and `saving` (adds `exportSession(key)`, not enumerable); a saved session's sources join `parsed` in key order, assembly runs over all of them, and `restoreSaved` puts back each one's agents and the links its own records made. Assembly leaves a saved step's missing evidence and its `startedSession` and copy notes as saved (`_saved`, in memory only). `threadsOf` in `lib/replay/assemble.mjs` draws threads again over the links given back. The reverse lookup reads a saved step's gh pull requests from `_prRefs`.

- `lib/replay/index.mjs`: `buildWorkHistory({ config, from, to, timezone, roots, scope, quietMs, git, goals, privateText, hiddenSessions, usage, keepRaw, updates, signal, onProgress })` returns the history: `sessions`, `agents`, `threads`, `events`, `links`, `anomalies`, `coverage`, plus `stateAt(t, { thread })`, `timeline` and `threadTimeline(id)` (`cursorAt`, `step`, `seekWhere`, `stateAtCursor`), the views `overview()`, `thread(id)`, `session(key)`, `turn(id)`, `event(id)`, and `record(eventIdOrRef)`. `toJSON()` is deterministic and holds no file paths; it throws for a `privateText` history. `privateText` swaps the redactor for `createSecretsOnlyRedactor()` from `lib/redact.mjs` and passes `privateText` to the parsers, which then keep a private source's content (`hide`) while still adding nothing to its joins (`priv`); `assemble.mjs` keeps its agent type, description and models. Tests: `test/private-text.test.mjs`. `hiddenSessions` (`'skeleton'` by default, or `'redacted'`; anything else throws) keeps the full redactor and passes `ctx.hiddenSessions` to the parsers and `assemble.mjs`, which treat `'redacted'` as `privateText` treats a private source (`hide` is false, `priv` stays true); the history's `hiddenSources` is empty, so `record()` projects a private record instead of `shapeOnly`, and sessions keep their titles. `toJSON()` doesn't throw for it. Tests: `test/hidden-sessions.test.mjs`, which records child processes by patching `node:child_process` and calling `syncBuiltinESMExports()`. `usage` and `keepRaw` pass `ctx.usage` and `ctx.keepRaw` to the parsers, which skip `usage` for a skeleton source (`hide`) and `keepRaw` for every private one (`priv`), and `index.mjs` leaves private sources out of `cwdOfSource`; `assemble.mjs` moves a resumed copy's raw error text with its result; `createUsageCollector()` and `keepRawOn()` in `parse-common.mjs` hold the shared parts, and `usageCalls()` in `index.mjs` drops copied Claude Code messages by the harness's message id, which never leaves the engine. Tests: `test/replay-usage.test.mjs`.
- Excerpts: `redactClip(s, max, redact)` in `parse-common.mjs` collapses whitespace (`collapse`), then calls `redactThenCut`, which redacts the whole text, keeps the cut-then-redacted piece when the whole redaction starts with it, and otherwise cuts the whole redaction at `placeholderSafeEnd`. `redactClipFirstLine` redacts before it splits off the first line (a hook's refusal reason, a words-only goal citation). The adapters' `text()` and `cut()` use `redactClip`; `record()`'s `project()` uses `projectString` in `index.mjs`; `goalCitations(goal, { redact })` and `goalMembership({ ..., redact })` get the history's redactor. Where the engine compares a value the harness wrote (a queue's `absorbed_mid_turn` reason, a hand-back's `completed` status), it compares the collapsed raw value, never the redacted excerpt; the hand-back's is kept as a `_status` that isn't serialized. Tests: `test/redact-before-cut.test.mjs`, which also checks its list of cut lengths against the adapters' source and fails on any other cut or first line in `lib/replay` that its allowed list doesn't explain.
- Each event keeps `facts` (recorded), `derived`, `inferred` (each with its rule id), and `missing`; `lib/replay/evidence.mjs` holds the contract, checked on every event before a history is returned.
- Who sent a Claude Code user record: `originOf(rec)` in `claude.mjs` reads `origin.kind`, else `turnOrigin` (`task_notification` becomes `task-notification`), and `fromProgram(rec)` is `turnOrigin === 'sdk'`. A program's turn becomes `delegation-received` or `agent-message` with `actor: 'program'` and `facts.from: 'program'`, and a program's command a `command` with the same; `isExecInstruction` in `lib/problems/context.mjs` (which also takes a program's `command`, so a run a program opened with a slash command is checked) and the goal watch in `goals.mjs` treat `from: 'program'` as they treat `codex-exec`. Tests: `test/replay-turn-origin.test.mjs`, on made-up records in `test/fixtures/replay/turn-origin.mjs`, with the reading the engine gave before it read `turnOrigin` kept in `test/fixtures/turn-origin-legacy-reading.json`.
- `lib/replay/sources.mjs` finds files by the timestamps inside them; `claude.mjs` and `codex.mjs` parse one file each in file order, sharing `parse-common.mjs`; `assemble.mjs` de-duplicates, links, applies the clock rules, and builds turns and threads; `outcomes.mjs` asks git through `lib/git.mjs`; `timeline.mjs` folds points with snapshots; `views.mjs` renders the drill-down; `metrics.mjs` defines each counted thing once for both; `classify.mjs` holds every inference rule (`RULES`) and the parsers; `ids.mjs` makes ids from SHA-256 spelled in the letters a to p, so the redactor never alters them; `jsonl.mjs` reads lines with their byte offsets.
- Non-interactive Codex runs are `codex exec`; Codex's patch tool is `apply_patch`. `lib/replay/codex-program.mjs` holds the pure readers for today's format: `readExecProgram` (a tokenizer and literal reader that lists a program's `tools.*` calls and says whether they run straight), `programOutcome` (the output's status line, error and printed results), `itemCommand` and `fileChangePatch` (the item records). `codex.mjs` builds the events: `startProgram`, `item`, `attachTo` and `finishProgram`.
- The timeline's state at a moment carries `countEvidence`, the level of each running count, on the same terms as the views' metrics.
- `lib/replay/` ships inside the package's `lib/` folder, and `honestweek view` builds its history with it, so its interface may still change.
- Goals and lookup: `buildWorkHistory({ ..., goals })` takes the goal record; with it the history gains `goals` (in `toJSON()` too) and the view `goal(id)`. `lookup(query)` takes a string or a query from `parseLookup(text)` (exported from `lib/replay/index.mjs`) and returns `{ query, kind, sessions: [{ session, evidence, ambiguous?, refs: [{ via, evidence, rule?, pr?, repository?, ambiguous?, event, count }] }], goals, notes, rules }`, where a pull-request pointer's `repository` is `{ owner, name }` (null for a part it doesn't name) and `ambiguous` is `{ owners: n }` or `{ ownerUnknown: true }`, where `rules` maps each rule id the refs name to its description. A pull-request query is `{ kind: 'pr', owner, repo, number }`. A file lookup adds `repositories: [{ repo, roots, sessions }]`, and each of its session rows names its `repo`. Each goal is `{ id, title, state, members: [{ session, evidence, ambiguous?, joins: [{ type, evidence, rule?, event, count, ambiguous?, detail }] }], unmatched: [{ kind, ref, where?, why }] }`.
- `lib/replay/goals.mjs` reads the goal record (`normalizeGoalRecord`, `goalCitations`) and builds membership (`goalMembership`, `goalView`); `lib/replay/lookup.mjs` holds `parseLookup`, the reference index both share (`createReferenceIndex`), and `createLookup`. The parse-time scan is `createWatch` in `parse-common.mjs`: the adapters get it as `ctx.watch` (null for a private source) and push `{ token, where, event }` notes onto `joins.watched`; Claude Code's push, branch, and worktree records go onto `joins.branches`. Both lists move onto the kept copy of a record in `assemble.mjs` like the other joins, and neither adds a fact to any event.
- The rules `pr.gh-command`, `pr.squash-subject`, and `goal.prompt-names-id` are in `LOOKUP_RULES` in `classify.mjs`, apart from the event rules in `RULES` that `assertEventContract` checks; the history's `rules` merges both only when `goals` is given, and `describeRules` gives a lookup result's `rules` and a `goal(id)` join's `ruleText`. `prRefsInCommand` implements the first rule. File paths are compared through `keyPath` in `ids.mjs`, the form `pathKey` hashes. A repository's checkouts (`rootsOfRepo` in `index.mjs`) are its configured path, `attributionRoots` from `lib/worktrees.mjs` (the same folders sessions are attributed by, read from the repository's metadata without running git), and `worktreeList` in `lib/git.mjs` (`git worktree list --porcelain`). Squash subjects come from `lookupCommit`. Neither git call is made for a display-role repository or with `git: false`. The history's `_repoRoots(label)` (not enumerable) returns a copy of a readable configured repository's checkouts by its label, or null for a display-role or unknown one; its first call for a label can run `git worktree list`. Owner matching is `prMatches` and `matchPrRefs` in `lookup.mjs`; the ambiguity ranking is `effectiveRank`; a call that never ran is `didNotRun`; a Codex call's working folder is kept on its event as `_workdir`, which isn't serialized.
- Launch links: `lib/replay/launch.mjs` holds `launchKind(command)` (a `claude` word with `-p` or `--print`, or `codex exec`, read outside quoted text one command at a time), `matchLaunches({ launches, children, knownIds })` and `LAUNCH_RULES`. `claude.mjs` keeps in memory a program's opening turn (`joins.programStart`, its full text) and a Stop hook's own strings (`joins.hookLaunches`), and `codex.mjs` keeps a `codex exec` run's opening the same way; neither is written anywhere. `assemble.mjs` reads the shell calls from each step's in-memory command, matches them, sets the run's `launchedBy` (`{ event, session, evidence, rule }`, or `{ ambiguous: true, evidence, rule, launches, sessions }`), and adds a `program-launch` link `{ from: <step id>, to: <session>, evidence, rule, sessions: [launcher, run] }`. The history's `rules` gains `LAUNCH_RULES` only when a session has `launchedBy`, so a history without one is byte-identical to before. Tests: `test/program-launch.test.mjs`, on made-up logs in `test/fixtures/replay/program-launch.mjs`, with the reading the engine gave before the join kept in `test/fixtures/program-launch-before.json`.
- Phrase search: `lib/replay/words.mjs` holds `wordsOf`, `isReference` (the Find page's own rule, kept as `isRef` in `lib/view/assets/search.js`, plus the `pr:`, `pull:`, `commit:` and `path:` prefixes), `matchWords(h, text)`, `similarPrompts(h, eventId)` and `WORD_RULES`; `lib/replay/word-index.mjs` holds search everywhere (`buildWordIndex`, `createWordSearch`, `cutRedacted`, `excerpt`). `lib/view/data.mjs` shapes their matches into `/api/words` and `/api/search`, which answer as they did before the move; `test/ask.test.mjs` pins their matches, order, evidence and excerpts on the demo week. The page's `isRef` and `isReference` agree on every input that test names, prefixes included.
- The commands: `lib/ask.mjs` builds the week the way `view` does (`ownWeek` in `lib/view/own-week.mjs`, or the demo week from `lib/demo/week.mjs`), asks `createViewData` in this process for `/api/lookup`, `/api/words`, `/api/search`, `/api/replay`, `/api/problems`, `/api/home` and `/api/goal`, never with `private=1`, and shapes each answer into its own JSON, marking log and goal-list text `{ quoted }`. Tests: `test/ask.test.mjs`.
- `tools/replay-inspect.mjs --demo` imports `buildCorpus({ goals: true })` from the test fixtures, so it runs only from a clone.
- Tests: `test/replay-model.test.mjs`, `test/replay-timeline.test.mjs`, `test/replay-units.test.mjs`, `test/replay-harness.test.mjs`, `test/replay-regressions.test.mjs` (one test per defect the independent review found), `test/replay-goals.test.mjs` (goal membership, lookup, and the tool's new commands), the clean-room fence in `test/site-cleanroom.test.mjs`, over the synthetic corpus in `test/fixtures/replay/corpus.mjs` (its goal sessions are added only with `buildCorpus({ goals: true })`, so the other tests read the corpus they always did).
