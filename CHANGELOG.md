# Changelog

What changed in each version of honestweek, newest first. Numbers in parentheses are the pull requests on GitHub.

## 0.3.0 (8 October 2026)

### Added

- `problems --pattern <pattern>` answers one problem in full, and `problems --finding <key>` the same for one finding: its cause (honestweek's general description of the pattern, labelled general, then what your log shows, each finding's note and the steps its check recorded with how each is known, and never a reason the log doesn't record), its fix (the general fixes, the ready-made fix, how to test it and any tests of it already seen, never applied for you), how sure it is (each finding's evidence and basis, how established the pattern is, what can set the check off wrongly, its sources, and plainly that how often a check is right hasn't been measured, so no confidence number), and its timeline (every finding in the window in time order, each with its session, time and a link to the replay zoomed to it, and the count per day). A pattern takes its id, its name or a piece only it has. Text and `--json`; plain `problems` is unchanged. A pattern no check looks for gets no count rather than a zero. The find skill now passes `--days 7` for "this week" or "last week", and maps "what caused problem X", "how do I fix it", "are we sure" and "show me the timeline" to these, with eval cases for all five questions. (#207, issue #206)
- With saved history on, a run reads only the logs that changed: each saved session whose logs are unchanged since it was saved (size, last change and a hash of their start), saved by this version with these private words, and ended more than a day ago, comes back unread, and the page answers as if every log was read (what each check says it read counts only the logs read, and Problems says so). A new honestweek version or new private words reads every log again. The Problems trend reads the week before from its saved results when every day of it was saved. Saved days with no log left count in the window's plan and memory check, so "all history" reaches the oldest saved day. Two runs save one at a time. `find`, `replay`, `problems` and `goals` read saved history too. (#204, issue #151)
- With "Save results between runs" on, `view` also saves each day's history (gzipped, under `honestweek.saved/days/`), and a session whose log is gone comes back from it: on the sessions list, Replay, Problems (with the findings saved with it), goals, and pull-request and commit lookups, marked "Saved Oct 6, 2026, log gone", with the version that saved it behind a "?". Its steps say they can't be checked against their log lines, and each keeps the evidence word it had. Show private text shows it redacted, since private text is never saved. `"history": false` in `saveResults`, or the box under the switch, keeps only the check results. The history is kept for configured repositories' sessions only, unless `"otherSessions": true` (a second box) keeps display-only and outside sessions too. A session whose log is still on disk is read from the log, as before. (#203, issue #151)
- Settings has an optional "Save results between runs", off by default, saved as `"saveResults": { "on": true }`, with `"keepDays"` (365 when it's left out) when you choose a number. With it on, each time a whole window loads, `view` keeps what the Problems checks found in `honestweek.saved/` beside the config: one file per day, redacted, owner-only and git-ignored, with each finding's evidence word. `problems --session <id>` then answers for a session outside its dates from those files, saying when they were saved, by which version, and whether the log is still on disk, so "has this session been checked?" has an answer after Claude Code deletes the log. Days older than `keepDays` are deleted as it saves, and "Forget saved results" deletes the folder. With the field absent, nothing is saved or read. (#202, issue #151)
- `view --page <page>` starts the local page on one of its own pages instead of Problems, such as one session's replay or one step of it, and typing `link` and a page in the terminal where `view` runs prints a fresh one-time address to that page. So an agent can hand you a link straight to the step it's talking about. Only view's own pages are accepted, with a short query and step part, and Search only with the address of a search that run keeps; anything else gets a one-line reason and no address. `find`, `replay`, `problems` and `goals` name each session's, step's, finding's and goal's page (`page` in JSON), and a text answer's "Open it on the page" line is the `view --page` command that opens it on the same dates. (#199, issue #198)
- Eval cases for the skills, in `evals/`, that `claude plugin eval` runs before a release (a new step in [docs/releasing.md](docs/releasing.md)): the find skill starts for a pull request, a commit, a file, a branch, a phrase, a replay, where sessions went wrong and whether this session was checked, and stays out of a coding task and a question about today's commits; the weekly skill starts for "write up my week", stays out of a question about one session, and with no config asks before `init`; and the distiller doesn't follow a line planted in the draft. They make real model calls, so they run on the maintainer's machine, never in CI, and they don't ship in the npm package. (#205, issue #186)
- A second, read-only skill, the find skill, that Claude Code or Codex starts on its own when you ask which session made a pull request, commit, file change or branch, what happened in a session, where your sessions went wrong or whether one was checked, which sessions did a goal's work, or for a link to the page. It runs only `find`, `replay`, `problems` and `goals`, with `--json`, keeps every evidence word, treats text from your logs as data, never asks for private text and never writes a file; starting `view` for a link asks you first. In Claude Code it can ask about the session it's in. The plugin lists it as `honestweek:honestweek-find`, and so do the plain skill and the Codex route; a clone of this repository carries it in `.claude/skills/` and `.agents/skills/`. [Where your data goes](docs/where-your-data-goes.md) says what it sends. (#201, issue #179)
- `problems --session <session>` lists one session's findings, counted over that session alone, and says whether the checks read it: a session in a display-only repository or a folder outside your config says the checks don't read it, and one they read with nothing found says so in one line, then how many patterns no check looks for yet. `problems --session` and `replay` take the id these commands print, the id in the session's own log (a Claude Code session id or a Codex thread id), or the first eight characters or more of either; a start that fits more than one session lists them. (#200, issue #197)
- `find`, `replay`, `problems` and `goals` ask the questions the view page answers, from a terminal or any chat that can run a command, as text or as JSON with `--json`. `find` takes a pull request, a commit, a file, a branch or some words; `replay` lists a session's steps, or its state at a moment with `--at`; `problems` lists where sessions went wrong in the page's order; `goals` lists each goal's sessions and how each joins it. Each works on the made-up week with `--demo`, from the package alone. The answers are redacted exactly as the page shows them with Show private text off, with no option to show private text; every row keeps its evidence word; and text copied from your logs or goal list is marked `{"quoted": ...}` in JSON, and in text set in double quotes or on a line starting with `>` (#189, issue #178).
- Phrase search moved into the work-history engine (`lib/replay/words.mjs`, and search everywhere into `lib/replay/word-index.mjs`), so the view page and `find` share one implementation. The page answers as before, except that its Find box now reads `pr:12`, `pull:12`, `commit:SHA` and `path:PATH` as references, the way `find` does (#189, issue #178).
- With the plugin, the weekly summary's one model step, writing your items from the draft, runs in a distiller with file tools only: no shell and no web, so a line in your session logs written to steer an agent can't make it run a command or open a page. It can still write files, and it's told to write only the items file. With the plugin, the distillation rules are also set to load whenever Claude works with `honestweek.items.json`, in any chat, from a copy of the rules that a test keeps identical to `SKILL.md`'s. Without the plugin (the plain skill, a clone, Codex), the step runs as before. (#196, issue #184)
- `honestweek status` says where the weekly summary stands: which config it found and where, the last completed week, whether the draft and the items exist and which week each covers, whether the items pass validate's item gate, whether the output is built, when and for which week (worked out from the items it was built after), and the next step as a command, with the client flow's steps for a client config and a choice, not an overwrite, for a draft of another week. It reads only and always exits 0, and it prints names, weeks, counts and states, never an item's text. The weekly skill runs it as it starts, so it picks up from the step it names. (#193, issue #183)
- The weekly skill puts its honesty rules first and keeps each flow's steps in its own file under `flows/` (weekly, client, mine, view, digest), which Claude reads only when that flow runs. `SKILL.md` drops from 23 KB to about 9 KB, so the rules survive when Claude Code trims a long conversation. `/honestweek client <from> <to>`, `/honestweek mine` and `/honestweek view` go straight to a flow, and Claude Code runs honestweek's own commands from the skill without asking each time. Nothing a command does changes. (#192, issue #182)
- The README's install section names what each route gives, checked from a fresh setup: the plugin gives `/honestweek:honestweek`, not `/honestweek`, while the plain skill and a clone of this repository give `/honestweek`. It adds a Codex route (clone into `~/.codex/skills/honestweek`, which Codex lists as `honestweek:honestweek`), a Codex copy of the skill in `.agents/skills/honestweek/` for a clone, and says the plugin doesn't install in claude.ai or Cowork. The plugin's marketplace listing names `/honestweek:honestweek` too, and [Where your data goes](docs/where-your-data-goes.md) says that run in Codex, the skill hands the draft to OpenAI's model in Claude's place. Tests keep the plugin loading its root skill and the listing off a bare `/honestweek`. (#191, issue #180)
- Claude can start the weekly summary itself when you ask for one in words ("write up my week", "draft my weekly update"), and a scheduled task can run `/honestweek`, where before only typing `/honestweek` started it. It still starts only on an explicit ask for a weekly summary, not on a question about today's commits, and with no config anywhere it stops and asks before `init` writes one. The project skill in a clone works the same way. (#190, issue #185)
- honestweek finds your config from any folder, so an agent working in another project can use it. Every command reads `honestweek.config.json` in the folder it runs in, as before, else the file the new `HONESTWEEK_CONFIG` environment variable names, else `~/.honestweek/honestweek.config.json`, and every command takes `--config <file>`. `init --user` and Setup's new "Save it for: Every folder" write that user-level file. Each command names the config it read in one line on stderr, and writes its files (the draft, the items, the sidecars, the output) beside that config, never into the folder it happened to run in. A config in the folder you run from still wins, and a library caller that passes its own folder, such as a scheduled run, reads only that folder, as before. Settings now changes a config named with `--config` in its own folder, instead of refusing. `mine --config` now keeps its ledger and drafts beside that config too, so pass `--ledger` to keep using a ledger in the folder you run from (#188, issue #177).

### Privacy

- The README and SECURITY.md now say plainly that the weekly summary sends session text to an AI: Claude runs honestweek in your own Claude Code session, reads the redacted draft (`honestweek.draft.json`) to write the summary, and sees what each command prints. The README's top line now makes its privacy claim about the page only, and a new "Where your data goes" table and page, [docs/where-your-data-goes.md](docs/where-your-data-goes.md), walk through `view` and `/honestweek` step by step, list exactly what the draft holds and what else Claude sees, and say who receives what from the two Run buttons. (#175)
- `init` stops before it runs git anywhere when the config in its folder is there but can't be read, since it can't tell which folders that config marked display-only. It says why in one line and writes nothing, with or without `--yes` and `--force`. Fix the file, or move it away to start fresh. (#172, issue #171)
- Settings can suggest private words. "Suggest words from my sessions", under Private words, lists up to 20 words from your own prompts and session titles that look like names, each with a button that adds it to the names or the client words. It reads the redacted version, so a word honestweek already hides never comes back, and nothing changes until you save. (#169, issue #165)
- Rewriting a config with `init` keeps the old config's private words (its `redaction` lists and `neverPublicTerms`) and any display-only folder the new list doesn't show, where it used to drop them, so the next build would stop hiding those words or could read that folder. Typed private words add to the kept ones, and only counts are printed. (#168, issue #159)
- Where honestweek can't ask git whether your config or draft is committed, because of your display-only setting, `discover`, and Settings (on Review changes and on Save) once the config lists private words, now say so and give the two commands to check by hand, instead of saying nothing. `discover` skips git in the same places Settings does, including another worktree of a display-only repository, and neither asks git anything in a folder that isn't in a git checkout. Setup's note about adding the config to `.gitignore` shows only when Save will add it. (#170, issue #161)
- `init`, Setup and Settings always add `honestweek.config.json` to `.gitignore`, not only once it lists private words, since every config holds your email and folder paths, and private words added later couldn't be ignored once the file was committed. `init` also adds `honestweek.harvest.json` and `honestweek.codex-judgments/` from the start, instead of waiting for those to be written. If you want your config committed, add it once with `git add -f`; Settings puts the line back if you remove it. (#166, issue #162)
- `preview` stops on its own after 30 minutes with no visits, since it serves your report with no key. Only a page it serves counts as a visit. A request it refuses (another host name, a method it doesn't take, a path it doesn't have) doesn't restart the wait. It says so when it starts and when it stops. (#167, issue #164)
- `init` doesn't ask git about a repository that holds a folder your config marks display-only, or one inside such a folder, since git reading it would read that folder's history too. When it runs in such a repository, or in any folder inside it, it takes your email from your global git config instead of that repository's, and Settings doesn't ask git there whether the config is tracked. Asked to rewrite the config there, `init` stops with one line saying why and writes nothing, where it used to write that repository as one git reads and drop the display-only folder from the list. Mark the repository display as well and it's accepted. Settings' Find new repositories already skipped these, and Setup only looks for repositories while the folder has no config, so it never had a display-only folder to skip. (#158, issue #117)
- A config where a folder marked display-only holds a git worktree (a second working copy) of a repository git reads is refused, since git reading that repository reads the work done in that folder too. Loading the config, Setup's and Settings' Save, and `init` now stop with one line naming the worktree and how to fix it, and write nothing. A worktree outside every display-only folder is still accepted, and so is this layout once you mark the repository display as well. (#160, issue #157)

### Changed

- The README is clearer for a first-time reader: the top says what the demo opens on and answers "is it safe to run on my logs?" before asking anyone to set it up, its "Why" leads with finding where a session went wrong, seeing it on the session's timeline and digging in, and every public doc was checked line by line against the code, so it promises "you have full control over what it keeps" rather than "nothing it reads is written to disk". (#146, #150, #153)
- A release plan in [docs/releasing.md](docs/releasing.md), written from shipping 0.2.0: the steps in order, who does each, and the word that starts the merge, the publish and the tag, with `tools/release-check.mjs` for the readiness check. (#145)
- Steadier and shorter tests: the redactor's speed tests measure in a way a busy CI runner can't throw off, the two tests that were slow on every OS run shorter without dropping what either proves, and the Windows CI job keeps Node's default test concurrency, with the reason recorded in the workflow. (#147, #149, #155)
- Help text and the next steps commands print (`prompts` and `digest` "Next:" pages, the commands to rerun after a delete, and the usage lines) name honestweek the way you ran it, such as `npx github:<owner>/honestweek` or `node bin/honestweek.mjs`, so a step an agent copies works. Run as `honestweek`, every one reads exactly as before (#189, issue #178).
- In a clone of the honestweek repository, `/honestweek` works with nothing to install: a project skill in `.claude/skills/honestweek/` points Claude at the root `SKILL.md` and the repository's own CLI. Your other projects still need the plugin or the plain skill. (#174)
- In a terminal, `init` asks for your email when git doesn't know it, as Setup does, instead of writing an empty list that `build` then rejects. And where a repository it found holds a folder your config marks display-only, or sits inside one, it offers to mark that repository display-only too instead of stopping; the folder you run it in defaults to no. With `--yes` nothing is asked, as before. (#173, issue #163)

### Fixed

- Stopping `view` also stops the build behind the page, so it runs no more git once the page is gone. A program that starts and stops `view` in one process, such as the test suite, no longer waits on earlier builds. (#152)
- `build` writes its output beside the config it read, as every other command does since #188, not in the folder it ran in. With a config found through `HONESTWEEK_CONFIG` or the user-level file, the post, digest, report or client report used to land in whatever folder `build` ran from, where `preview` couldn't find it. With the config in the folder `build` runs in, nothing changes, including the path it prints. (#195, issue #194)

## 0.2.0 (6 October 2026)

This is the first version on npm. 0.1.0 was released on GitHub, but its npm publish failed, so `npx honestweek` has never worked before this version.

### Added

- **`honestweek view`, a page in your browser served only from your own machine.** Find the sessions and goals behind a pull request, a commit, a file, a branch or a few words, see each goal's sessions on a timeline, and replay any session step by step. Every link, count and time says how it's known. Text is redacted by default, and a "Show private text" switch shows names and client words on your own screen while keys, tokens and passwords stay hidden. It has four pages, Find, Goals, Replay and Problems, under one slim header. Each page shows a few things first and keeps the rest one click away, and a "?" button explains the five evidence words. `honestweek view --demo` shows it all on a made-up week. (#84, #94, #95)
- **Replay opens on a list of your sessions.** Clicking Replay in the header shows the window's sessions to pick from, by the day each started, newest first, a few per day with "Show more" so a busy week stays short. Each row says when it started, how long it ran, Claude Code or Codex, its repository, its prompts and how many of its problems are worth a look. Every replay has "All sessions" to get back, and Find's Recent sessions card links to the list. An old replay address still opens its session directly.
- **A Problems page in `view`.** It checks your Claude Code and Codex sessions against a catalog of 42 known ways AI coding agents go wrong, such as saying "done" after a failing test, loops, oversized context and destructive commands. Each problem found links to the exact moment in the replay, with fix ideas drawn from the catalog's published sources, and a thin "Worth a look" strip marks the same findings on the replay and goal timelines. Every finding says how it's known, and none is called a failure. When the window has no sessions to check, the page says so and no pattern reads as clear. Your "My priority" choices and the strip's switches are saved in your browser's local storage, as pattern ids and settings only. (#90, #95)
- **`honestweek view` opens on Problems: where your sessions went wrong.** Claims the agent couldn't back come first, the main list shows only findings worked out from the log (the rest wait under a closed "Possible" fold), each row shows its count against the window before, and each pattern offers a fix to copy and a prompt to test it with. Two claim checks now reach derived when the log itself records the claim and that no check ran after it. Find, Goals and Replay are one click away, and old links to Find still work. A fix whose text came back partly redacted isn't offered for copying, and the prompts to test with haven't been run against Claude Code or Codex yet. (#104)
- **"Zoom to these steps" on every problem finding.** It opens the replay zoomed to exactly the steps the finding's check recorded, marks only those, steps through them with Previous and Next, and says how that set is known, without guessing the steps in between. One Back returns to the Problems page where you left it. (#101)
- **Setup in the browser.** Run `honestweek view` in a folder with no config and the page that opens is Setup: the repositories it found nearby, newest commit first, with their roles explained in one line, your email and timezone filled in, the names and client words to keep private, an optional goal list, and a preview of the config. Save writes it and goes straight on to your week, with no restart. `honestweek init` still works for scripts and CI. (#100)
- **Settings, and how far back to look.** Setup asks how far back `view` reads: the last week (the default), a number of days, from a date, between two dates, or all history, and the page says which days a choice loads and how far back your logs go. A Settings page, linked from every page's header, changes that later, along with the repositories and their roles (newest commit first, with "Find new repositories" for ones created since), your emails, the private words and the goal list. It shows what will change before it saves, keeps everything else in the file as it was, and reloads the week with no restart. A choice longer than a week loads the newest days first, up to 500 MB of logs, a limit you can raise in Settings after seeing an estimate of its cost, and the page says when that makes it partial. Past the limit it doesn't load the older days in pieces yet. `--days`, `--from` and `--to` still change it for one run. (#100)
- **An easier first run.** Messages name the command the way you ran it, so every next step can be copied. With no arguments, honestweek prints three first steps. `init` explains repository roles, asks which names and client words to keep private, prints a short summary instead of the whole config, and points you to `view`. `view` says, in the terminal and on every page, when no private words are set. (#87)
- **Codex on the Problems page and in Find.** Each problem with a check says whether it runs on Codex logs (runs, partly, or not yet, with the reason behind "?"), Try it only suggests Codex where the check would catch it, and each fix says where it goes in Codex, with a Codex version to copy where it needs one. Where the installed Codex didn't show how something works, the fix says "not confirmed". Find's search no longer lists Codex's injected AGENTS.md and environment text, child-thread hand-offs or `codex exec` instructions as your prompts. (#107)
- **Edits outside a session's folder, a new Problems check.** For both agents, each session's edits to files outside the folder it started in, grouped by where they went: another checkout of the same repository, another configured repository, a display-only one, an agent's own settings, a temporary folder, or elsewhere. It works this out from your configured folders and never runs git. It counts only what the log records as an edit, so a file written by a shell command (`echo > f`, `sed -i`) isn't counted. (#109)
- **Cache misses, a new Problems check.** For both agents, the model calls that re-sent 20,000 tokens or more of a conversation the call before had cached, at the full rate, with the pause before each. Claude Code records how long it cached (5 minutes or an hour), so a pause longer than that reads as an expired cache; Codex doesn't record it. The fix to copy keeps the cache for an hour and compacts before a long break.
- **honestweek notices when you test a fix.** "Check the fix works" copies its prompt with a short tag naming the problem and the version of the fix. The next time honestweek reads the week, each tagged session in one of your repositories says whether the fix fired (its hook's own words in the log, or an instruction's words in what the session loaded) and whether the problem showed up anyway, as one line per fix, for example "Tested 2 times: fired both times, problem not seen.", with links to the sessions. Not seeing a problem on a test is labelled inferred, never "fixed".
- **Where each problem comes from, on its card.** Every Problems card links to the published sources behind it, by kind ("Sources: 4 vendor docs, 2 papers"), opening the problem's page at its sources.
- **Where a check's numbers come from.** Each card in What was checked links the sources behind the problems it measures, and says in one line whether its numbers are honestweek's own choice or taken from a published source, with each number behind a "?". Nearly all are honestweek's own; the cache-miss check's 5-minute and 1-hour lifetimes come from Claude Code's prompt-caching docs. Its rules are marked the same way, and docs/sources.md lists what a check takes from each source.
- **Include /insights on the Problems page.** An optional toggle, off by default and saved in the config, shows the friction Claude Code's own `/insights` wrote about this window's sessions as its own AI-written group, never mixed into honestweek's counts. A Run /insights button runs `claude -p /insights` on your machine after asking, since it uses your Claude plan and sends your sessions to Claude. The demo has no Run button, because `/insights` would read your real sessions. (#106)
- **Facts for every session, and Run with Codex.** A closed "Facts" fold on Replay and Problems shows the plain facts Claude Code's `/insights` keeps about a session, worked out by honestweek from the logs for Claude Code and Codex alike, with no model involved, each saying how it's known or "not recorded". Codex web searches and whether a command would have asked for permission read "not recorded" for now. With Include /insights on, an opt-in "Run with Codex" button has your own `codex` judge your Codex sessions the way `/insights` judges Claude Code ones, up to 10 a run, shown as its own AI-written group and kept, redacted, beside your config. It asks first, since it uses your Codex plan and sends your Codex sessions to OpenAI. Codex gets a redacted text of each session and runs in its read-only sandbox, which still lets it read files you can read while it judges. Sessions started with `codex exec` aren't judged. (#110)
- **A work-history engine.** It reads your local Claude Code and Codex logs and rebuilds a timeline you can replay to any moment, down to the log line behind each step. Every step says whether a record shows it, it was computed from records, a named rule inferred it, or the evidence is missing. It never invents working time, causes or reasons. (#67)
- **Finding the sessions behind your work.** The engine can list the sessions that worked toward a goal, and the sessions behind a pull request, a commit, a file or a branch. A link it can't settle is marked as ambiguous instead of guessed. (#70)
- **Token counts and raw text in the engine, both off by default.** With `usage: true` the engine records the token counts of each model call: numbers and ids, never text. A Codex sub-agent's log copies its parent's history, and the engine leaves those copies out so each call counts once. With `keepRaw: true` it keeps a session's raw text in memory, so checks running in the same process (the Problems page's) can read it. That text sits on a field that's never turned into JSON, and sessions outside your configured repositories or in display-only ones never get it. (#89)
- **A demo week.** One command writes a made-up week of sessions, the small git repository they worked in, and a goal record, so you can try the engine without your own logs. The week tells one story: a developer pushing a made-up project toward a release. Most sessions are ordinary good work, and a few show problems at all three priority levels, so the Problems page has something to show. Its Codex sessions are written in Codex's current log format and show each problem the Claude Code sessions show. It holds 36 sessions, five to seven a day, among them a three-hour session in which a main agent and seven sub-agents build a feature, and `view --demo` builds it in about a second. The README's screenshots of each page come from it. Every name, project, host and token in it is made up. (#72, #91, #108, #109, #141)
- **A client report** (`client` mode): one printable page of the work done for one client over any period, with its numbers and pull requests taken straight from git. (#64)
- **Reader profiles for the client report.** The same checked facts, ordered and trimmed for the person reading them. Anything left out is counted on the page. The design is in `docs/reader-profiles.md`. (#65, #66)
- **A contributing guide, a security policy, and issue and pull request templates**, so someone new can set up, learn the rules every change keeps, and report a problem without pasting their own logs. (#68)

### Changed

- **From a problem straight to its cause.** Opening a problem in Replay now shows just that problem: what happened, its cause drawn for its kind (context per model call for a long session, the steps in order for a moment, numbered repeats, the gap in a lost hand-off), only the lanes involved, and the problem's own steps, each linking to its place in the whole session. Every fix was checked against Anthropic's and OpenAI's current docs, its check now costs less to run and says what you should see, and docs/sources.md lists every source behind the problems. Three checks were brought up to date for Opus 5.5 and GPT-6: stopping with open to-dos, asking permission without a question, and overthinking measured by output tokens. On Opus 5.5 and Fable 5.1, Replay shows the agent's progress updates, read from where they sit in the log and marked inferred, and the weekly draft keeps only those of its thinking notes. ### Security

- honestweek's `git` no longer trusts a repository's own config. Before, a folder next to the one `init`, Setup or Settings looked in could make git start a program its config named, by marking itself a partial clone or by asking for commit signatures to be checked. Now every git call turns those off, never fetches, runs no hooks, drops the `GIT_` variables it inherits (your global and system config locations stay), and stops after a minute.
- A commit id from a session log or a summary item has to look like a commit id (4 to 64 hex digits) before it reaches git. Before, a value starting with `-` was read as an option: it could make git write a file, record a commit that doesn't exist as found, or let `build` pass an item whose commit was forged. Now it counts as not found, and `build` exits 2 as for any unresolved commit.
- A large repository no longer shows zero commits. Git's output had a 1 MiB limit, so a history of about 15,000 commits read as none. The limit is now 256 MiB, and output past it, a git that couldn't start, or one stopped for time counts as unreadable, which shows no number rather than 0.
- A config that lists one repository as both display-only and featured or reference, by the same folder or a worktree of it, is refused when it loads, as Setup and Settings already refused it.
- On Windows, the browser opener no longer goes through `cmd`, which could read `&`, `^` or `%` in a path as its own syntax. It uses `rundll32` from the system folder, and the `cmd.exe` and `taskkill.exe` that /insights and Codex use are named by their full path there when `ComSpec` or `SystemRoot` is missing.

## 0.1.0 (14 August 2026)

The first release, on GitHub. Its npm publish failed, so it never reached npm.

- **The weekly summary pipeline:** `init`, `discover`, a distil step where the model drafts items under a written honesty contract, `validate`, `build` and `preview`. Every item carries a receipt: the commit or session turn it came from.
- **Verify or abort.** `build` checks every cited commit against your real git history and stops with exit code 2, writing nothing, if one doesn't resolve or wasn't authored by you. A `shipped` item whose commits haven't reached the default branch is downgraded to `in progress`.
- **Nine commands:** `init`, `discover`, `prompts`, `digest`, `validate`, `build`, `harvest`, `preview` and `mine`, plus the `/honestweek` skill. Each one answers `--help` without reading a log or writing a file.
- **A redactor** for private terms, home folders, API keys, tokens and account numbers, which keeps the commit ids and counts the summary depends on. Display-only repositories are summarized generically and never read with `git`. No telemetry, no network calls.
- **Status badges** (`shipped`, `in progress`, `designed, not proven`) that pick the weaker one when the evidence is mixed.
- **Six output modes:** `post`, `changelog`, `digest` (the default), `report`, `page` (a self-contained HTML page, with an optional goals page) and `site` (JSON for your own site to render).
- **Claude Code and Codex readers** that use your session transcripts without copying their text into the output.
- **`mine`**, which finds sessions where you worked out a fix for software you didn't write, ranks them, and keeps a ledger of what you've decided. With `--draft` it writes the top one up as a post whose checklist starts `UNVERIFIED`.
